# 콘텐츠 제작 화면

```
pip install -r requirements.txt
python run.py            →  http://127.0.0.1:8000
```

키 없이도 돈다. 그때는 2~9단계 선택지가 `data/fake.py` 의 테스트 데이터로 나온다.

## .env

```
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-4o-mini
OPENAI_MODEL_STRONG=
TAVILY_API_KEY=
```

| | |
|---|---|
| `OPENAI_MODEL` | 기본. 독자·검색의도·각도·유형·제목·근거 |
| `OPENAI_MODEL_STRONG` | 상위. 구조와 최종 산출물. 비우면 기본과 같아진다 |
| `TAVILY_API_KEY` | 근거 검색. **비우면 검색 없이 돌고 명제가 전부 미확인으로 남는다.** 오류가 안 나므로 `/api/health` 의 `search` 로 확인한다 |

나머지 단계는 후보를 여러 개 내고 사람이 고른다 — 몇 개가 시원찮아도 나머지에서
고르면 되니 모델이 조금 약해도 버틴다. 구조는 다르다. 글 전체의 뼈대라 잘못 잡히면
뒤가 전부 흔들리고, 사람이 소제목 목록만 보고 판단하기도 어렵다.

어느 프롬프트가 어느 등급을 쓰는지는 `llm.py` 의 `STRONG` 한 곳에서 정한다.
호출하는 쪽은 모델을 고르지 않는다. `GET /api/health` 로 지금 무엇이 잡혔는지 볼 수 있다.

`.env` 는 git 에 올리지 않는다. 키가 있으면 2~9단계 선택지를 모델이 만들고,
없으면 테스트 데이터로 떨어진다. 키가 있는데 호출이 실패하면 조용히 넘어가지 않고
화면에 이유가 뜬다 — 뭐가 돌았는지 화면만 보고 알 수 있어야 하기 때문이다.

**폴더 기준은 파이프라인의 시점이다.** `steps/` 는 고르는 동안, `output/` 은 다
고른 뒤. `record/` 만 기준이 다른데, 기록은 어느 시점에도 걸치는 별개 관심사라
그렇게 뒀다. `external/` 은 밖으로 나가는 것만 모았다.

**단계 하나는 폴더 하나다.** 그 단계의 프롬프트 입력, 후보 생성, 확정값 스키마,
직접 쓴 값 읽기, 화면 문구, 프롬프트 원문이 전부 그 폴더에 있다. 독자 단계를
고치려면 `steps/reader/` 만 열면 된다.

각 폴더는 `STEP` 하나를 내보낸다(`steps/step.py` 의 `Step`). dataclass 로 둔
이유는 규약이 코드로 강제되기 때문이다 — 모듈 속성 규약으로 두면 이름에 오타가
나도 조용히 `None` 이 되고, 그 단계만 화면에서 비어 보인다.

**단계 폴더는 다른 단계 폴더를 import 하지 않는다.** 앞 단계 값은 항상 드래프트
dict 에서 키로 읽는다(`pay(d, "reader")`). 이걸 어기면 순서를 바꿀 때 import 가
꼬이고 "이 폴더만 보면 된다" 가 성립하지 않는다. `test.py` 가 검사한다.

**정제 헬퍼는 `sanitize.py` 한 곳에만 있다.** `_s` 하나가 여섯 폴더에 복사되면
자르는 길이가 달라지거나 한쪽만 고쳐지고, 그런 어긋남은 예외 없이 조용히
지나간다. 이것도 `test.py` 가 검사한다.

**순서는 `steps/__init__.py` 의 `order(draft)` 한 곳이 정한다.** 번호(`no`)도
거기서 매긴다. 폴더 이름에 번호를 붙이면(`01_reader/`) 순서를 바꿀 때 import
경로가 다 깨지고, 폴더가 자기 번호를 들면 하나를 끼울 때 나머지를 다 고쳐야 한다.

**순서가 리스트가 아니라 함수인 이유는 채널 때문이다.** 홈페이지와 네이버는
제목·구조·집필이 다르므로, 채널이 정해지면 그 채널의 단계가 공통 뒤에 붙는다.
정적 리스트로 두면 두 채널 단계가 항상 다 보이고 사람이 자기 채널이 아닌
단계로 들어갈 수 있다. `GET /api/draft/{key}` 가 "이 드래프트가 지나가는
단계인가" 를 검사하는 것도 같은 이유다.

`BY_KEY` · `TIERS` · `WRITE_HINT` 는 순서와 무관한 속성이라 전역으로 둔다.
key 로 단계를 찾는 일은 어느 드래프트냐와 상관없이 같은 답이어야 한다.

**단계 폴더는 `steps/` 바로 아래 있다.** 한때 `common/` 층을 두고 그 옆에
`site/` · `naver/` 를 만들 자리로 비워 뒀는데, 채널을 폴더가 아니라
프롬프트로 가르기로 정해서(`Step.by_channel`) 그 자리를 안 쓰게 됐다.
형제가 없는 `common/` 은 "옆에 common 아닌 게 있다" 는 거짓말이고, 그 안의
`outline` · `title` 은 채널마다 다르게 도니 common 도 아니었다. 걷어냈다.

**채널이 갈리는 지점은 두 곳에 이름으로 드러나 있다.**

```
steps/outline/site.md · naver.md      단계 안 — 무엇을 요구하는가
output/site/ · output/naver/          승인 뒤 — 어떻게 조립하는가
```

층을 넣었다 뺀 자국이 하나 남아 있다. `steps/{key}/` 로 경로를 조립하던
프롬프트 등록이 층이 생길 때 깨졌었다 — 지금은 import 해 온 모듈이 자기
자리를 알려 준다(`DIR_OF`). 층을 없앤 지금도 그대로 둔다. 규칙으로 경로를
유추하지 않는 편이 층이 다시 생기든 말든 안전하다.

**단계마다 다른 것은 폴더가 들고, 모든 단계에 똑같이 벌어지는 일은 레지스트리에
있다.** 후보 캐시, 자취 남기기, 실패 기록, 직접 쓰기 디스패치가 그렇다.

1단계(소재)와 8단계(승인)는 폴더가 없다. 소재는 화면 흐름 자체가 다르고(별도
엔드포인트, `state`, 평가 반영) 승인은 고를 게 없다. 레지스트리에 메타만 등록한다.
소재는 시트를 붙일 때 폴더로 뺀다.

`write` 와 `hero` 도 `steps/` 에 없다. 승인 이후에 도는 것이고 후보를 고르는
단계가 아니다. 섞어 두면 레지스트리가 `ORDER` 에 넣을지 말지로 계속 헷갈린다.
`output/` 에 두고 프롬프트만 옆에 붙였다.

## 프롬프트는 등록해서 찾는다

파일이 단계 폴더로 흩어졌으므로 이름에서 경로를 알아야 한다. 규칙으로 유추하지
않고(`reader` → `steps/reader/prompt.md`) **명시적으로 등록한다.** 규칙 기반은
이름에 오타가 나면 다음 규칙으로 조용히 흘러가거나 엉뚱한 파일을 집는다.
등록해 두면 없는 이름은 `MissingPrompt` 로 그 자리에서 터진다.

등록은 각 단계가 import 될 때 `steps/__init__.py` 가 하고, `write`·`hero` 는
자기 모듈이 한다. 같은 이름을 두 번 등록하면 막는다 — 단계를 복사해 만들다가
`key` 를 안 바꾸면 뒤엣것이 앞엣것을 덮어쓰고, 그러면 엉뚱한 프롬프트가 도는데
아무 데도 티가 안 난다. 지금 등록된 것은 `GET /api/health` 의 `prompts` 로 본다.

## 모델 등급

`llm.generate(name, payload, strong=False)`. 어느 단계가 상위 등급을 쓰는지는
그 단계 폴더가 `Step.strong` 으로 들고 있고, `llm.py` 는 등급을 모델 이름으로
바꾸기만 한다.

**등급을 넘기는 것과 모델 이름을 고르는 것은 다르다.** 등급은 그 단계가 무엇을
결정하느냐에 달린 성질이고, 모델 이름은 설정(`config.py`)이다. 부르는 쪽은
여전히 `gpt-...` 를 모른다. 전체 매핑은 `GET /api/health` 의 `tiers` 로 한눈에
볼 수 있다.

지금 상위 등급은 `outline` 과 `write` 둘이다. 나머지 단계는 후보를 여러 개 내고
사람이 고르니 몇 개가 시원찮아도 버티지만, 구조는 글 전체의 뼈대라 잘못 잡히면
뒤가 전부 흔들리고 본문은 고를 여지 없이 나온 그대로 나간다.

## API

| | |
|---|---|
| `GET /api/health` | 키·모델·등급·등록된 프롬프트·로그 위치 |
| `GET /api/steps` | 단계 8개 정의 |
| `GET /api/logs` | 로그 세 갈래를 합쳐서 본다 |
| `GET /api/topics?state=` | 소재 목록 |
| `POST /api/feedback` | 소재·후보·결과물 평가 |
| `GET /api/draft/upload` | 올려 둔 근거 문서 목록 |
| `POST /api/draft/upload` | 근거 PDF 올리기 (multipart) |
| `DELETE /api/draft/upload/{id}` | 문서 지우기 |
| `POST /api/topics/pick` | 소재 확정 |
| `GET /api/draft` | 드래프트 상태 |
| `GET /api/draft/{key}` | 단계 화면에 필요한 것 (`?refresh=1` 이면 후보 새로 뽑기) |
| `POST /api/draft/{key}` | 단계 확정 |
| `POST /api/draft/write` | 본문 작성. 8단계까지 다 정해져야 부를 수 있다 |
| `GET /api/draft/result` | 결과물 두 갈래 + 발행 전 확인 목록 |

응답은 늘 `{ok: true, ...}` 또는 `{ok: false, reason: ...}`.
`reason` 이 `no_topic` / `skipped` / `incomplete` / `no_body` 면 프론트가 해당 화면으로 보낸다.
`llm_failed` 면 `detail` 에 이유가 담겨 화면에 그대로 뜬다.
**어디로 보낼지는 프론트가 정하고, 백엔드는 "덜 됐다"만 알려 준다.**

## 따로 띄우려면

`run.py` 의 `app.mount` 를 지우고 백엔드만 올린 뒤,
프론트는 아무 정적 서버로 서빙하고 `/api` 를 백엔드로 프록시한다.
쿠키를 쓰므로 다른 도메인이면 CORS 설정이 필요하다.

## 결과물은 채널 하나만 만든다

예전에는 본문 하나로 두 결과물을 만들었다. 그러면 문체·구조·CTA 가 같고
표현만 다른 글이 둘 나온다. 지금은 채널을 2단계에서 고르고 **본문부터 그
채널로 쓴다.**

`render.build(d)` 는 `{channel, capture, checklist, site, naver}` 를 주고
고른 쪽만 채운다. 화면은 온 쪽만 그린다.

**갈리는 것과 안 갈리는 것을 나눴다.**

| | 갈리나 | 왜 |
|---|---|---|
| `render.py` | 갈린다 | HTML 조립과 에디터 마크업은 다른 일이다 |
| `write.md` · `hero.md` | 갈린다 | 프롬프트가 진짜 다르다 |
| `write.py` · `hero.py` | 공통 | 입력 조립·검증은 채널 무관 |
| `figures.py` | 공통 | 컴포넌트 넷은 같다 |

`write.py` 를 복제하지 않은 이유는 `sanitize.py` 를 한 곳에 모은 것과 같다 —
복제하면 한쪽만 고쳐지고 그 어긋남은 조용히 지나간다. 채널 분기도 코드에 두지
않는다. 규칙은 `channels.for_write(ch)` 로 주입받고 프롬프트는 이름으로 고른다
(`site_write` · `naver_write`). `test.py` 가 `write.py` 에 채널 이름 분기가
없는지 검사한다.

**두 렌더러는 서로를 import 하지 않는다.** 한쪽이 다른 쪽을 부르면 네이버가
홈페이지의 파생물이 되어 채널을 가른 뜻이 없어진다. 공유는 `common.py` 를
통해서만 한다. 이것도 `test.py` 가 검사한다.

## 프롬프트에도 층이 있다

본문 작성 프롬프트는 370줄인데 채널 차이는 문단 길이·말투·도입부 정도다.
통째로 복제하면 한쪽만 고쳐진다. 그래서 밑바탕을 깔고 채널 파일은 차이만 적는다.

```
_write.md          공통 — 블록 · 근거 다루기 · 도식 데이터
{채널}/write.md     차이 — 누가 읽나 · 분량 · 말투 · 하지 않는 것
_common.md         사실성 · 출력 형식
```

`prompt.register(name, path, base=...)` 로 걸고 이 순서로 조립한다. 뒤에 읽은
것이 더 잘 지켜지므로 겹치는 규칙은 채널 쪽이 이기고, 맨 뒤 공통 규칙은
어느 쪽도 못 뒤집는다.

## 구조·제목은 폴더가 아니라 프롬프트가 갈린다

`steps/site/` · `steps/naver/` 를 만들지 않았다. 두 채널의 구조·제목 단계는
**화면도, 후보 고르는 법도, payload 도, 순서도 같다.** 다른 것은 "LLM 에게
무엇을 요구하는가" 뿐이고 그건 프롬프트 차이지 단계 차이가 아니다.

폴더를 가르는 것은 이런 때다 — 채널마다 화면이 다르거나, 저장 모양이 다르거나,
단계 순서가 다르거나, 채널 전용 로직이 있을 때.

그래서 `Step(by_channel=True)` 하나로 처리한다.

```
_prompt.md  →  site.md      →  _common.md
공통             채널 델타         사실성 · 출력 형식
```

레지스트리가 `site_outline` · `naver_outline` 두 이름으로 등록하고,
`STEP.prompt_of(채널)` 이 부를 이름을 고른다. `write.py` 가 하던 것과 같다.

**자취의 원문도 실제로 부른 이름에서 가져온다.** `key` 로 찾으면 그 단계 행에
원문이 안 붙는다 — 갈라 놓고 한 번 놓쳤던 자리다.

## 확정값 모양은 채널과 무관하다

제목 확정값에 `meta_description` · `slug` · `main_keyword` ·
`secondary_keywords` · `tags` 가 **늘 다 있다.** 채널에 안 맞는 것만 비운다.

채널마다 다른 필드를 내면 저장·API·화면·결과물이 전부 양쪽을 알아야 한다.
그리고 **비우는 일도 코드가 한다** — 프롬프트에 "빈 값으로 두라"고 적어
두었지만 안 지키는 날이 있고, 그때 네이버 결과물에 엉뚱한 슬러그가 붙는다.

## 검사는 OS 를 가정하지 않는다

개발은 리눅스에서 하고 실제로 쓰는 곳은 윈도우다. 윈도우에서 돌렸더니 넷이
실패했는데 **앱 버그는 하나도 없었고 전부 검사가 리눅스를 전제한 것**이었다.

```
grep 호출              윈도우에 없다
경로가 "/" 로 시작      C:\... 은 아니다
한글 파일명 하드코딩     zip 을 거치며 인코딩이 깨지는 환경이 있다
read_text() 인코딩 생략  윈도우 기본은 cp949 라 한글이 깨진다
```

넷 다 막는 검사를 뒀다. 금지어를 문자열로 세지 않고 **실제로 무엇을
하는지**를 본다 — 문자열로 세면 그 검사 자신의 설명에 걸린다.

## 배포 문서가 코드와 어긋나지 않게 한다

`deploy/README.md` 와 `운영.md` 는 사람이 서버를 세팅할 때 보는 것이라,
낡으면 **조용히 잘못 세팅된다.** 실제로 그랬다 — `TAVILY_API_KEY` 가 문서에
없어서, 그대로 따라 하면 근거 검색이 꺼진 채 돈다. 오류가 안 나므로 결과물을
보고서야 눈치챈다.

그래서 `test.py` 가 문서를 검사한다.

```
.env 의 모든 *_KEY 가 배포 문서에 채워 넣을 줄로 있다
문서가 보라고 하는 값을 /api/health 가 실제로 준다
키가 없으면 run.py 가 뜰 때 알린다
문서의 로그 폴더 이름이 record.STREAMS 와 같다
```

마지막 것은 `trail/` 하나였던 로그가 셋으로 갈렸을 때 문서만 옛 이름을 들고
있던 자리다.

## 채널 정책은 한 객체다

`data/channels.py` 의 `ChannelPolicy` 하나가 채널이 코드에 요구하는 것
전부를 든다. `hard_rules` · `render` · 전역 `MEDIA_LABELS` 로 흩어져 있던
것을 합쳤다 — 흩어져 있는 동안 라벨이 두 곳에 생겨 **같은 것을 "캡처" 와
"자료 화면" 으로 다르게 부르는** 일이 실제로 났다.

```
자르는 것    max_sections · max_figures · max_callouts · max_tags
비우는 것    meta_required · tags_allowed · media_allowed
조립이 읽는 것 figure_render · hero_ratio · trust_block · cta_strength
이름         labels
```

`frozen=True` 다. 이건 설정이라 돌다가 누가 고치면 그 세션만 다르게
동작하고 재현이 안 된다.

## 채널 판별은 한 곳이다

`channels.channel_of(d)` 하나만 쓴다. 예전에는 **넷이 각자 했다** — 순서
계산, 본문 프롬프트 고르기, 대표 이미지, 결과물 조립. 우연히 같은 답을 내고
있었을 뿐이라 한 곳만 고치면 조용히 어긋난다.

**예외가 하나 있고 그건 의도한 것이다.** `steps.channel_of()` 는 모르면
빈 문자열을 준다 — 순서를 정하는 자리라 **"아직 안 정함" 과 "홈페이지" 를
구별해야 한다.** 조립 쪽은 모르면 홈페이지로 떨어뜨린다. 결과물 만드는
중에 터지면 사람이 할 수 있는 게 없다.

## 채널별 순서를 따로 선언한다

```python
SITE_ORDER  = [...]
NAVER_ORDER = [...]      # 지금은 내용이 같다
```

같은 리스트 객체를 두 키가 가리키면 **한쪽에 단계를 끼울 때 다른 쪽까지
바뀐다.** 나중에 네이버에만 사진 준비 단계를, 홈페이지에만 서비스 연결
단계를 넣게 되면 여기만 고치면 된다.

**채널별로 폴더를 가르지는 않았다.** 지금 차이는 프롬프트 내용과 제한값
뿐이고, 순서·화면·입출력 계약·실행 흐름 중 하나가 실제로 달라지는 날 가른다.
그전에 가르면 내용이 95% 같은 파일이 두 벌 생기고 한쪽만 고쳐진다.

## 채널 규칙은 코드가 읽는 값만 둔다

`data/channels.py` 가 든다. `skeletons.py` 와 같은 자리, 같은 이유다 —
프롬프트에 박으면 두 채널 규칙이 매 호출에 실리거나 공통 규칙이 두 벌로
복제된다.

| | 무엇 | 누가 지키나 |
|---|---|---|
| `hard_rules` | 상한과 조립 방식 | 코드가 강제한다 |
| `guidance` | 권장 범위·문체 | 모델이 참고한다 |
| `capabilities` | 쓸 수 있는 수단 | **필수 목록이 아니다** |

처음에는 `elements` 를 한 목록으로 두려 했는데, 그러면 모델이 모든 글에 핵심
요약·목차·서비스·강조 박스를 억지로 넣는다. 채널은 갈렸는데 **모든 글이
똑같아진다.** 그래서 "필요하면 쓸 수 있다" 로만 읽히게 하고 프롬프트에도
그렇게 적었다.

**수량은 상한만 강제한다.** 하한을 적으면 모델이 그 수를 채우려고 없는 도식을
만든다 — `_common.md` 에 이미 적힌 원칙이다. `figure_range` 의 하한이 0 인
것이 그래서다. 도식이 필요 없는 글에는 도식이 없어도 된다.

## 네이버 도식은 여전히 캡처한다

도식 데이터는 한 벌이고 `figures.py` 도 한 벌이다. 두 채널이 각자 그리면
어긋나지만 하나에서 나오면 어긋날 수가 없다.

**바뀐 것은 어디서 찍느냐다.** 예전에는 홈페이지 미리보기에서 찍었는데,
채널이 갈리면서 네이버 드래프트에 홈페이지 결과물이 없다. 지금은 네이버
결과물이 `figures` 배열로 도식 마크업을 따로 낸다. 번호는 본문 자리표시
(`[도식 N 삽입]`)와 같다 — 다르면 어느 그림을 어디에 넣을지 알 수 없다.

캡처 폭·글자 크기는 `channels.CAPTURE` 가 정하고 화면이 받아 쓴다. 네이버는
휴대폰에서 읽히므로 폭이 좁고 글자가 크다. 화면에 박아 두면 서버와 두 곳을
맞춰야 하고, 안 맞으면 조용히 다른 그림이 나간다.

**SVG·PNG 렌더러를 따로 만들지 않았다.** 한글 줄바꿈과 높이 계산을 코드로
다시 만드는 일이고, 무엇보다 렌더러가 둘이 되는 순간 "어긋날 수가 없다" 가
깨진다. 네이버 비율 문제는 캡처 스타일로 푼다.

## 색은 한 곳에서 온다

`data/brand.py` 가 정한다. 전에는 같은 색이 `figures.CSS` · `render` 의
`BODY_CSS` · 프론트 `app.css` 세 군데에 있었고, 한 곳만 고치면 나머지가 조용히
어긋났다.

결과물 HTML 은 CSS 변수로 받는다(`--bs-accent`). 사람이 맨 위 한 줄만 고쳐
사이트 색에 맞출 수 있다.

**다만 기본값을 함께 싣는다**(`var(--bs-accent, #2B8AE0)`). 도식을 이미지로
저장할 때 화면 밖에 복제해 찍는데, 그때 `.post` 바깥이라 변수 선언이 안 잡힌다.
값은 `brand.py` 한 곳에 있고 문자열을 만들 때 끼운다.

## 작성자·검토자를 지어내지 않는다

홈페이지 결과물의 신뢰 요소 — 작성자, 검토자, 관련 서비스 — 는
`data/company.py` 에서 온다. **모델이 만들지 않는다.** 이름을 지어내면 신뢰
요소가 정반대로 작동하고, "환경 전문가" 같은 임의 문구로 빈칸을 메우는 것도
같은 문제다.

값이 없으면 **그 영역을 통째로 빼고 렌더한다.** 지금은 비어 있어서 아무것도
안 나가고, 대신 발행 전 확인 목록에 "작성 주체 없음" 이 뜬다 — 안 뜨면 사람이
뭐가 빠졌는지 모른다. 기준일은 사람이 없어도 나간다. 규제 정보는 언제 기준인지가
내용이기 때문이다.

관련 서비스도 같다. 소재에 붙은 `service_id` 로 `SERVICES` 에서 찾고, 없으면
아무것도 안 나간다.

## 로그는 세 갈래다

물어보는 질문이 달라서 파일부터 나눠 둔다. 한 파일에 섞어 두면 읽을 때마다
`kind` 로 걸러야 하고, 갈래마다 보존 기간이나 처리 방식을 달리하기도 어렵다.

| 폴더 | 무엇 | 언제 쌓이나 |
|---|---|---|
| `feedback/` | 사람이 남긴 평가 — 좋다·별로다·메모 | 사람이 버튼을 누를 때 |
| `choice/` | 사람이 고른 것 (`confirmed`) · 올린 문서 (`uploaded`·`rejected`) | 단계를 확정하거나 파일을 올릴 때 |
| `response/` | AI 가 내놓은 것 (`generated`·`written`·`failed`) | 후보·본문·이미지를 만들 때 |

전부 하루 한 파일, 한 줄에 한 건(JSON Lines)이다. 쓰기가 실패해도 예외를
올리지 않고 서버 콘솔에만 이유를 찍는다 — 기록은 곁가지고, 못 남겼다고
사람이 하던 작업이 멈추면 안 된다.

`choice` 행은 그 자체로 읽혀야 하므로 `offered`(그때 주어진 후보의 id 와
제목)를 함께 남긴다. `chosen` 만 남기면 "o0 을 골랐다"가 되어 `response` 와
조인하지 않으면 아무 뜻이 없다.

셋을 시간순으로 합쳐 보려면 `record/history.py` 를 쓴다. 합치는 일을 각
스트림 모듈에 두면 셋이 서로를 import 하게 되므로 별도 파일에 뒀다.
`GET /api/health` 의 `log_dirs`·`log_rows` 로 어디에 몇 줄 쌓였는지 볼 수 있다.

## 로그를 눈으로 볼 때

`GET /api/logs` 에 주소만 치면 JSON 으로 나온다. 파일을 하나씩 열면 세 폴더에
갈려 있어 순서가 안 맞고, jsonl 은 한 줄이 수십 KB라 편집기로 보기 어렵다.

```
/api/logs                        최근 100건 요약
/api/logs?stream=response        AI 가 낸 것만 (feedback | choice | response)
/api/logs?kind=failed            실패한 것만
/api/logs?kind=uploaded          사람이 올린 문서만
/api/logs?doc=6f4c74505c81       그 문서가 지나온 자취
/api/logs?sid=abc123             그 세션이 지나온 자취
/api/logs?step=outline           구조 단계 것만
/api/logs?day=2026-08-04&limit=0 그날 전부 (limit 0 이면 안 자른다)
/api/logs?order=asc              오래된 것부터 (기본은 최근 순)
/api/logs?full=1                 요약 말고 행을 통째로
```

응답에 `total`·`shown`·`counts`·`sids`·`steps`·`kinds`·`docs` 가 함께 온다.
**`counts` 는 필터를 탄 수다** — 예전에는 스트림 전체를 다시 세서, 같은 응답
안에서 `total: 0` 인데 `counts` 에 27 이 적혀 있었다.

**`step` 은 단계 key 다.** 프롬프트 이름이 아니다 — 채널이 갈려도
(`naver_outline`) 행에는 `outline` 로 남는다. 이걸 몰라서 실제로 막혔다.

그래서 **빈 결과일 때 무엇을 물어야 하는지 알려 준다.**

```json
{"total": 0,
 "asked": {"step": "naver_outline"},
 "available": {"steps": ["outline", "write", ...], "kinds": [...]},
 "hint": "step 은 단계 key 다 — outline 처럼 쓴다"}
```

결과가 있으면 힌트를 안 붙인다. 있는데 붙으면 잡음이다.

## 근거 단계가 한 줄로 요약된다

`claims` · `plan` · `search` · `check` 로그를 명제마다 뒤져야 알 수 있던 것을
`?step=evidence` 한 번으로 본다.

```
raw   {"본문_가져옴": 2, "가져오기_실패": 1,
       "상태별": {"supported": 2, "search_disabled": 3}}
항목  c01  supported · sufficient
      c02  unverified · insufficient   근거 검색이 꺼져 있습니다
```

"검색이 돌았나 · 몇 건 걸렸나 · 왜 미확인인가" 는 자주 묻는 것이라 한 자리에
모아 둔다.
`kind` 는 `generated`·`confirmed`·`written`·`failed`·`uploaded`·`rejected` 여섯이다.
`sids` 로 세션을 고른 다음 `?sid=` 로 좁히는 순서가 편하다.

**기본은 요약이다.** `raw` 와 `input` 이 한 행에 20KB씩이라 통째로 내보내면 화면이
열리지 않는다. 요약은 그 행이 무엇이었는지 알아볼 만큼만 남긴다 — 후보 개수와
제목, 고른 id 와 라벨, 평가와 메모, 실패 사유, `raw` 는 길이만. 자세히 볼 행을
찾은 다음 `full=1` 로 다시 부른다.

거른 뒤에 자른다. 자르고 거르면 "최근 100건 안에 그 sid 가 없어서 빈 결과"라는
헷갈리는 일이 생긴다.

## 평가 저장

1단계 소재, 2~9단계 후보, 최종 결과물 어디서든 좋음·별로와 한 줄 메모를 남길 수 있다.
전부 `POST /api/feedback` 한 곳으로 가고, `feedback/{날짜}.jsonl` 에 한 줄씩 붙는다.

```json
{"at": "...", "sid": "...", "step": "reader", "option_id": "p1",
 "verdict": "down", "tags": [], "note": "이 소재로는 팀장까지 안 간다",
 "option": {"id": "p1", "title": "제조사 환경담당 팀장", "payload": {...}},
 "prompt_input": {"topic": "CBAM 전환기간 종료와 본격 시행"},
 "model": "gpt-4o-mini"}
```

`option_id` 만 남기면 나중에 아무 의미가 없다. 2~9단계 후보 id 는 세션 한정
임시 번호라 `p1` 이 무엇이었는지 알 길이 없다. 그래서 후보 내용과 그것을 만들 때
프롬프트에 넣은 입력을 함께 남긴다. "이 입력을 주면 모델이 이걸 내놓고 사람은
이렇게 봤다"가 한 줄에 다 들어 있어야 프롬프트를 고칠 근거가 된다.

평가 표시 상태는 저장하지 않는다. 화면을 새로 열면 눌린 자국이 사라지고, 별로라고
한 후보도 다음에 그대로 나온다. 지금은 쌓는 것까지만 한다.

`feedback.read()` 로 전부 읽어 온다. 쓰기가 실패해도 예외를 올리지 않는다 —
로그를 못 남겼다고 사람이 하던 작업이 멈추면 안 된다.

## 어디서 기다리게 되나

프롬프트 호출은 두 지점에서 일어난다.

| | 언제 | 무엇이 도나 |
|---|---|---|
| `GET /api/draft/{key}` | 화면 열 때 | 그 단계 후보 생성 |
| `POST /api/draft/{key}` | 다음 누를 때 | **직접 쓴 값일 때만** 부속 항목 채우기 |
| `POST /api/draft/write` | 승인 화면에서 만들 때 | 본문 전체 + 도식 데이터 (제일 오래 걸린다) |

고르기로 넘어가면 POST 는 캐시를 쓰므로 즉시 끝나고, 다음 화면을 여는 GET 에서만
기다린다. 그때는 `불러오는 중…` 이 뜬다.

직접 쓰기는 POST 에서 한 번 더 돌아 그만큼 더 걸린다. 이 구간은 화면이 아직
넘어가지 않아 표시할 자리가 없으므로, 버튼을 잠그고 이름을 `정리하는 중…` 으로
바꾼다(`UI.busy`). 잠그지 않으면 안 눌린 줄 알고 다시 눌러 같은 프롬프트가 두 번
돌고, 두 번째 결과가 첫 번째를 덮어쓴다.

## 모든 프롬프트에 붙는 공통 규칙

`prompts/_common.md` 가 모든 프롬프트 뒤에 자동으로 붙는다. 두 가지가 들어 있다.

**아는 것을 쓰되, 확인이 필요한 것은 쓰지 않는다.** 입력이 제목 한 줄뿐이라
모델이 그 분야 지식을 쓰지 않으면 아무것도 못 만든다. 그래서 막지 않고 선을 그었다.

| 써도 되는 것 | 쓰면 안 되는 것 |
|---|---|
| 그 개념·제도가 일반적으로 무엇을 다루는지 | 시행 시점, 발표일, 기한 |
| 통상 쓰이는 용어와 절차 이름 | 수치, 비율, 금액, 건수 |
| 널리 알려진 구성이나 진행 순서 | 특정 기관의 결정·발표 내용 |
| 그 직무가 통상 부딪히는 문제 | 조항 번호, 문서 이름 |

판단 기준은 하나다. **"그건 사실이 아니다"라고 지적당할 수 있는가.**

개수 규칙이 따로 있다. `"5단계"` 처럼 수를 적으면 구조 단계가 그 수에 맞춰 섹션을
만들므로, 확신이 없으면 개수를 적지 않는다.

**출력 규칙.** JSON 하나만, 한글 키 금지, `id`·표시 문구·글자 수는 만들지 않는다.
모든 파일에 글자 하나까지 똑같이 들어 있던 문단이라 한 곳으로 모았다.

뒤에 붙이는 이유는 마지막에 읽은 규칙이 더 잘 지켜지기 때문이다. 파일이 고쳐지면
서버를 껐다 켜지 않아도 다음 호출부터 반영된다.

## 글 유형과 권장 구조

유형 6종(동향형·정보형·비교형·케이스형·가이드형·체크리스트형)의 권장 구조는
`data/skeletons.py` 에 데이터로 있다. 프롬프트에 넣지 않은 이유는 셋이다.

- 여섯 개를 다 실으면 쓰지 않을 골격이 매 호출에 실리고, 모델이 그쪽으로 샌다.
- 유형별로 프롬프트를 찢으면 공통 규칙이 여섯 벌로 복사된다.
- 구조 단계만 이 정보를 쓰는 게 아니다. 본문 작성과 이미지 생성도 같은 유형
  정보를 봐야 한다. 프롬프트에 박아 두면 세 곳에 복사된다.

구조 단계는 `skeletons.for_outline(유형)` 으로 **해당 유형 하나만** 프롬프트 입력에 싣는다.

## 구조와 이미지를 한 단계에서 정한다

어느 자리에 표가 필요한지는 그 자리에 무엇이 들어가는지 정한 다음에 알 수 있다.
나눠 놓으면 사람이 두 화면을 왔다 갔다 하며 같은 판단을 두 번 하게 되므로,
구조 단계에서 소제목과 이미지 계획을 함께 정한다.

```json
{"sections": [{"title": "무엇이 달라졌는가",
               "image": {"purpose": "서류 항목 차이를 한눈에",
                         "form": "전후 비교 도식"}},
              {"title": "지금 확인할 것", "image": null}],
 "hero_image": {"purpose": "...", "form": "..."}}
```

이미지 계획은 섹션에 붙여 둔다. 별도 배열로 두고 번호로 가리키면 섹션이 하나
늘거나 순서가 바뀔 때 조용히 엉뚱한 자리를 가리킨다.

**"무엇을 어디에"까지만 정한다.** 브랜드 색상, 규격, 비율, 생성 프롬프트 문구,
검수 항목은 이미지를 실제로 만드는 시점 일이라 이 단계에 없다. 대체 텍스트도
이미지가 만들어진 뒤에 쓴다.

소제목만 필요한 곳은 `steps.payload.titles(payload)` 를 쓴다. 제목 단계와 결과물
조립이 그렇다. 근거는 구조 앞으로 옮겨 가면서 이걸 더 이상 쓰지 않는다. 각자 payload 를 뜯지 않게 한 곳에 모아 뒀다.

`steps/type/` 의 `ARTICLE_TYPES` 이름과 `skeletons.TYPES` 의 키는 정확히 같아야 한다.
어긋나면 골격을 못 찾고 조용히 일반 구조로 흐른다.

## 직접 쓴 구조 읽기

구조 단계의 직접 쓰기 칸은 소제목과 이미지 계획을 함께 받는다. 규칙은 네 줄이다.

| 줄 | 어떻게 읽나 |
|---|---|
| `이미지:` 로 시작 | 바로 위 소제목의 이미지. 들여쓰기 무관 |
| `대표:` 로 시작 | 대표 이미지 |
| 그 밖의 모든 줄 | 소제목 |
| 빈 줄 | 무시 |

**바로 위 소제목에 붙인다.** 번호나 소제목 이름으로 가리키지 않는 이유는, 소제목을
고치거나 순서를 바꾸는 것이 이 칸의 목적이기 때문이다. 붙어 있는 줄에 붙이면
소제목을 고쳐도 연결이 끊기지 않는다.

구분자는 `—`, `–`, ` - ` 를 받고 없으면 전체를 형식으로 읽는다. 짧은 붙임표는
앞뒤에 공백이 있을 때만 구분자다 — 안 그러면 `Before-Process-After` 같은 형식
이름이 잘린다.

같은 규칙이 `frontend/js/shape.js` 에도 있다. 그쪽은 **타이핑하는 동안 결과를
보여 주는 용도**고, 확정값은 `steps/outline/parse.py` 가 만든 것을 쓴다. 규칙을 설명해
두는 것보다 지금 쓴 것이 몇 개로 읽혔는지 보여 주는 편이 잘 통하고, 오타가 나면
숫자가 안 올라가서 바로 보인다.

두 곳에 같은 규칙이 있는 것은 알고 있다. 타이핑마다 서버를 부르지 않고, 프론트가
보낸 값을 믿지도 않기 위한 선택이다. 어긋나도 숫자만 틀리게 보이고 저장되는 값은
백엔드 것이다.


## 도식은 생성하지 않고 그린다

회사 가이드의 `forms` 18개를 전부 확인해 보면 **하나도 빠짐없이 한글 글자가 곧
내용인 도식**이다. 분위기 이미지는 하나도 없고, 글자 없는 것은 `hero` 뿐이다.
그리고 `avoid` 규칙 중에는 생성으로 지킬 수 없는 것이 있다 — 가이드형의
"본문과 단계 수가 다른 이미지"는 생성 모델이 단계 수를 맞추지 못하므로
구조적으로 못 지킨다.

그래서 **글자가 뜻을 지고 있는가**로 쪼갠다.

| | 대표 이미지 · 썸네일 배경 | 본문 도식 |
|---|---|---|
| 글자 | 없다 | 글자가 곧 내용 |
| 만드는 법 | 생성 (아직 없음) | **마크업** (`figures.py`) |
| 홈페이지 | `<img>` | HTML 블록 그대로 |
| 네이버 | 같은 그림 | 그 블록을 이미지로 저장해 넣는다 |

**원본은 마크업 하나고 네이버 것은 거기서 파생된다.** 두 갈래가 각자 만들면
어긋나지만 하나에서 나오면 어긋날 수가 없다. 채널을 가른 뒤에도 이 성질은
그대로다 — 갈린 것은 렌더러이고 도식 데이터는 여전히 한 벌이다.

`forms` 18개는 컴포넌트 넷으로 묶인다 — 순서열 · 대조표 · 항목카드 · 구조도.
구조 단계는 이 넷 중 하나를 `form` 에 적고, 옛 이름이나 목록 밖 값이 오면
`figures.ALIAS` 가 흡수한다. 흡수하지 못하면 그 자리는 도식 없이 나간다.

`hero_image` 에는 `form` 이 없다. 대표 이미지는 도식이 아니라 상징 이미지다.
프롬프트가 hero 에도 form 을 요구했더니 실제 실행에서 세 후보가 전부 hero 를
"타임라인"으로 채운 적이 있어 필드째 없앴다.

## 같은 명제를 같은 본문에 두 번 대조하지 않는다

PDF 를 올리면 명제를 다시 만든다. 그때 **표현이 조금 흔들린다.**

```
1차  전환기간에는 CBAM 대상 수입품의 ... 적용되었다
2차  CBAM 전환기간에는 대상 수입품의 ... 적용된다
```

문구로 캐시를 잡으면 이걸 새 명제로 보고 **검증이 통째로 두 번 돈다.**
실제로 4분이 걸렸고 검색 14회 · 대조 20회였다.

**낱말이 얼마나 겹치는지로 같은 명제를 가른다.** 지문(해시)으로는 못 잡는다
— `적용되었다` 와 `적용된다` 는 앞 세 글자도 다르다. 조사·어미를 떼고
(앞 3글자) 8할 이상 겹치면 같은 명제로 본다. 종류가 다르면 다른 명제다 —
같은 문장이라도 규정과 해석은 대조 기준이 다르다.

열쇠는 셋이다.

```
본문 지문     주소가 아니라 내용. 같은 주소라도 글이 바뀌면 다시 대조한다
명제 열쇠     표현이 흔들려도 같은 값
판정기 판     프롬프트나 규칙을 고치면 올린다
```

**다시 대조해도 같은 답이 나오는 것만 담는다.** 상한에 걸렸거나 실패한 것은
다음번엔 될 수도 있다. 캐시는 **한 드래프트 안에서만** 산다.

## 검증된 명제는 확정에서 사라지지 않는다

**"안 고름 = 버림" 이 근거 단계엔 안 맞는다.** 화면이 `확인됨 · 공식 근거 ·
출처 3건` 이라고 표시해 놓고 다음을 누르면 사라지는 것은 앞뒤가 안 맞는다.

실제로 그렇게 났다. `supported` 3건 + `partial` 1건을 검증해 놓고 아무것도
안 고른 채 넘어갔더니 **구조가 받은 `claims` 가 빈 배열**이었다. 그래서 글이
근거 없이 추상적으로 나왔다 — "완료 기준", "책임 경계", "변경 지점" 같은
말만 남았다.

지금은 아무것도 안 골랐으면 `citable` 명제를 기본으로 담는다. 고른 것이
있으면 그 뜻을 따른다.

**문서는 명제가 아니다.** 한때 올린 문서를 확정값에 넣었는데, 그러면
"문서 제목이 사실인가" 라는 이상한 명제가 생긴다. 문서는 이미 `plan` 이
걸고 `check` 가 대조해서 **그 명제의 `sources` 에 들어가 있다.**

## `partial` 은 확인된 부분만 넘긴다

명제 전문을 주면 구조가 전체를 확인된 사실로 읽는다. 실제로 "모든 수입에
신고 의무" 가 확인된 것처럼 흘러갔다 — 원문은 50톤 미만 면제를 함께 말하고
있었다.

```
claim              모든 수입에 신고 의무가 적용된다
confirmed_parts    2026년부터 연간 신고 의무가 있다      ← 이것만 쓴다
unconfirmed_parts  예외 없이 모든 수입에 적용된다
```

## 근거가 없다는 것을 고르기 전에 알린다

결과물을 만든 뒤에 알면 늦다. 구조와 제목 화면에 뜬다.

```
근거가 하나도 없습니다. 구조는 소재·독자·각도만 보고 만들어지고,
본문이 사실을 단정하지 못합니다.
```

막지는 않는다. 다만 **사람이 구조를 고를 때 무엇을 감수하는지 알아야 한다.**

## 올린 PDF 자체가 사람의 선택이다

`doc:` 카드를 없애면서 **PDF 를 올려도 진행이 막혔다.** 목록에는 보이는데
고를 카드가 없어서 "다음" 이 `empty` 로 거절했다.

카드를 되살리지 않았다. **파일을 올리는 행위가 이미 "이걸 근거로 쓰겠다" 는
선택**이고, 카드로 또 고르게 하면 같은 판단을 두 번 시킨다.

확정 조건에 올린 문서를 넣는다. 다만 **`confirmed` 가 아니다** — 업로드는
원문 확보이지 주장 검증이 아니다. `unverified` 로 들어가 "이 문서에서
확인할 것" 이라는 뜻을 남긴다.

이미 담긴 문서는 다시 안 넣는다. 확정을 여러 번 하면 같은 문서가 그만큼
쌓인다.

## 왜 못 넘어가는지 갈라서 알린다

```
empty       고르거나 직접 쓴 것이 없다
no_sources  근거로 쓸 문서나 출처가 없다
```

`empty` 하나로 뭉개면 사람이 무엇을 해야 할지 모른다 — **PDF 를 올려 두고
막혔을 때 "빈 입력" 이라고 말한 것**이 실제 사고였다.

화면도 사유를 받는다. 예전에는 `fetch` 가 상태 코드만 던져서 "왜" 가 화면까지
안 갔다.

## 쪽마다 되풀이되는 줄은 쪽 이름이 아니다

```
4쪽  EU CBAM 본격 시행 대응 가이드 | 2026.08.06 기준
5쪽  EU CBAM 본격 시행 대응 가이드 | 2026.08.06 기준
```

**한 쪽만 봐서는 머리글인지 알 수 없다.** 문서 전체에서 같은 줄이 여러 쪽에
나오는지 세야 안다(위아래 두 줄씩, 40% 이상). 쪽 번호와 기준일만 있는 줄도
건너뛴다.

## 개발용 견본을 화면이 알린다

키가 안 읽히면 각 단계가 `fake.py` 로 떨어지는데, **화면만 봐서는 구별이
안 된다** — `t1a` · `c1` 이 떠도 잘 돌고 있는 줄 안다. 지우지는 않는다.
키 없이 화면 흐름을 보려고 둔 것이다.

`/api/health` 의 `mode` 와 단계 응답의 `mock` 으로 알린다.

## 근거는 검증된 명제다

근거 단계가 다섯 조각으로 돈다. 앞이 비면 뒤는 안 돈다.

```
claims   이 글이 성립하려면 참이어야 하는 것을 낱개로
plan     명제마다 어떤 질의로 어떤 성격의 자료를 찾을지
search   검색하고 본문을 가져온다
check    원문과 대조한다
policy   상태를 정한다
```

**카드 단위는 명제다.** 본문 작성이 받아야 하는 것은 "어떤 출처를 쓸
것인가" 가 아니라 "어떤 명제를 글에 쓸 것인가" 이고, 출처는 그 명제를
뒷받침하는 하위 정보다. 출처를 카드로 두면 같은 문서가 여러 번 뜨고 사람이
무엇을 고른 건지 모호해진다.

### supported 는 모델이 쓰지 않는다

모델이 자기 출력에 "이건 사실이다" 라고 적으면 그건 검증이 아니라 주장이다.
그래서 역할을 가른다.

| | 무엇을 |
|---|---|
| LLM | 의미가 대응하는가(`verdict`) · 원문의 **어느 대목**인가(`evidence_spans`) |
| 코드 | 그 대목이 원문에 실제로 있는가 → 상태 |

인용한 대목을 원문에서 못 찾으면 `invalid_check` 다. 한 번 다시 묻고, 그래도
못 찾으면 그 명제는 확인되지 않은 채로 남는다. **지어낸 인용에 출처가 붙는
것을 막는 자리**이고, 실제로 통과하지 못하는지 `test.py` 가 검사한다.

### 출처가 있다는 것과 확인됐다는 것은 다르다

예전에는 소재 기사와 올린 문서를 **카드로 따로 내면서 "출처 확인됨" 을
달았다.** 확인된 것은 주소가 존재한다는 사실뿐이었다.

| 확인된 것 | 확인 안 된 것 |
|---|---|
| URL 이 있다 | 그 기사가 이 주장을 뒷받침하는가 |
| 파일이 있다 | 지금 법령과 맞는가 |
| | 전환기간 기준인가 본격 시행 기준인가 |

그런데 그게 그대로 참고자료로 나갔다. 명제 쪽은 원문 대조까지 시켜 놓고
정작 기사·PDF 는 자동 통과하던 자리다.

지금은 **기사도 문서도 명제 안의 출처로 들어가 대조를 거친다.** 카드는
명제 하나뿐이고, 사람이 고르는 것은 "이 명제를 본문에 쓸까" 다.

올린 문서는 `plan` 이 **어느 명제에 걸지 고른다.** 모든 명제 × 모든 문서를
돌리면 상한을 금방 넘고, 문서 하나가 검색 근거를 다 밀어낸다.

### 원한 출처와 걸린 출처를 나눠 든다

검색 계획은 `official_primary` 를 **원했다**고만 말한다. 공식 원문을 노린
질의에서 기사가 나오는 일이 흔하고, 예전에는 그 기사에도
`official_primary` 가 붙어 우선순위 정렬이 무의미했다.

```
requested_target   계획이 노린 성격
actual_target      도메인을 보고 코드가 매긴 성격   ← data/sources.py
```

정렬도 자격 판정도 **actual** 로 한다. 목록에 없는 도메인은 `secondary` 다 —
잘못 낮춰 부르면 근거 하나를 덜 쓰지만, 잘못 높여 부르면 **블로그 글이 법령
행세를 한다.**

프롬프트는 여전히 기관 이름을 모른다. 아는 것은 출처의 성격뿐이다.

### 자격은 인용을 막지 않고 표현을 낮춘다

의미가 대응하는 것과 **그 출처가 그 말을 할 자격이 있는가**는 다른 축이다.
언론 기사가 법령을 정확히 요약했더라도 그 기사는 법령이 아니다.

```
status     supported      의미가 대응한다
authority  insufficient   규정 명제인데 기사만 있다
```

하나로 접으면(규정은 공식 원문 아니면 미확인) 공식 원문을 못 찾은 날 본문이
아무것도 단정 못 하고 **근거 없는 글**이 나온다. 그래서 상태는 살리고 본문의
표현 강도만 낮춘다 — "규정이 정한다" 대신 "◯◯ 보도에 따르면".

### 웹 원문도 앞부분만 자르지 않는다

법령 원문은 길다. 앞 12,000자만 넘기면 필요한 조항이 뒤에 있을 때
`insufficient` 가 나오고 짧은 기사만 근거로 남는다.

여기는 `pick.py` 와 상황이 다르다. PDF 는 한글 소제목 대 영문 원문이라
겹치는 낱말이 없어 LLM 이 필요했지만, **웹 원문은 영문 질의로 찾아온 영문
문서**라 낱말이 겹친다. 그래서 코드가 질의 낱말이 몰린 구간을 잡는다 —
호출이 늘지 않고, 하나도 못 잡으면 앞부분으로 떨어진다.

### 참·거짓이 아니라 다섯이다

| 상태 | 본문에서 |
|---|---|
| `supported` | 그대로 쓴다 |
| `partial` | **범위를 좁히고 조건을 붙여 쓴다** |
| `contradicted` | 쓰지 않는다. 반대 내용도 쓰지 않는다 |
| `unverified` | 사실로 단정하지 않는다 |
| `invalid_check` | 쓰지 않는다 |

참·거짓만 두면 **부분적으로 뒷받침되는 주장과 완전히 틀린 주장을 구분하지
못한다.** `partial` 이 있어야 본문이 `unsupported_parts` 를 빼고
`limitations` 를 반영해 쓸 수 있다.

**고를 수 있는 것과 인용할 수 있는 것은 다르다.** 추론(`inference`)은
미확인이어도 고를 수 있지만 출처를 달면 안 된다 — 원문이 없기 때문이다.
`policy.selectable()` 과 `policy.citable()` 이 그 둘을 나눠 정하고,
`is_confirmed()` 가 그것을 부른다. 판단이 두 곳에 흩어졌다가 어긋난 적이
있어서 한 곳에 둔다.

### 인용 대조는 정규화한 뒤에 한다

원문 그대로 비교하면 **정상 인용도 걸린다.** `pypdf` 는 하이픈 분철을 남기고,
웹 본문에는 유니코드 따옴표가 섞이고, 모델이 인용을 옮기며 공백을 흘린다.
공백을 접고 따옴표를 통일한 뒤에 찾는다. 12자 미만 인용은 우연히 맞으므로
받지 않는다.

### 스니펫으로 판정하지 않는다

검색 결과에 딸려 오는 스니펫은 앞뒤 조건이 잘리고 검색어가 든 문장만
강조된다. 그것으로 판정하면 PDF 앞 6,000자만 잘라 쓰던 것과 같은 실패다.
스니펫은 **어느 것을 가져올지 고르는 데만** 쓰고, 본문을 못 가져온 출처는
대조에 태우지 않는다.

### 기관 이름을 프롬프트에 박지 않는다

찾을 곳은 `source_target`(출처의 성격)으로만 받는다 — `official_primary` ·
`domestic_official` · `standards` · `research` · `secondary`. 성격 → 우선순위는
`policy.PRIORITY` 가 정한다. 프롬프트에 기관명을 박으면 다른 주제에서
재사용이 깨지고, 모델은 그 기관이 실제로 그 자료를 내는지 확인할 수 없다.

국문과 영문 질의를 둘 다 만든다. 국문만 쓰면 해외 제도의 원문 대신 국내
기사의 해석이 근거가 되고, 영문만 쓰면 국내 적용과 정부 안내를 놓친다.

### 상한이 곧 예산이다

명제 × 질의 × 본문 × 대조가 곱해져 호출 수가 된다. 상한이 없으면 프롬프트가
명제를 열둘 내는 날 그대로 터진다.

```
MAX_CLAIMS 6 · MAX_QUERIES 2 · MAX_FETCH 2 · MAX_CHECKS 12 · MAX_RETRY 1
```

**넘쳐서 못 본 것을 버리지 않는다.** `reason_code` 를 달아 미확인으로 남긴다 —
조용히 사라지면 왜 그 근거가 없는지 알 수 없다.

캐시는 질의별·URL별 두 벌이고 드래프트에 붙는다. 같은 원문이 여러 명제를
뒷받침하는 일이 흔해서, 없으면 한 편에 같은 문서를 대여섯 번 가져온다.

### 검색을 안 한 것과 못 찾은 것은 다르다

키가 없어 검색을 아예 안 한 것과, 검색했는데 자료가 없는 것은 **사람이 할
일이 다르다.** 앞은 키를 넣거나 원문을 올리면 되고, 뒤는 명제를 다시 세워야
한다. 뭉쳐서 "확인 필요" 로만 보이면 어느 쪽인지 모른다.

```
search_disabled     검색이 꺼져 있다
no_search_result    검색했는데 쓸 만한 것이 없다
fetch_failed        찾았는데 본문을 못 가져왔다
```

**안 찾아본 것은 고를 수 있다.** 안 그러면 키가 없는 날 고를 근거가 하나도
없어 사람이 막다른 길에 놓인다. 인용은 여전히 못 한다.

`search.run()` 은 **꺼져 있어도 부른다.** 부르는 쪽에서 거르면 "검색을 안
했다" 가 자취에 안 남는다.

### 켤 수 있는지를 상수로 복사하지 않는다

```python
ENABLED = api.ENABLED      ← import 시점 값이 굳는다
def enabled(): return api.ENABLED
```

굳혀 두면 그 뒤에 키가 들어와도 옛 값을 든 채로 남고, **두 곳이 다른 답을
내면서 오류는 안 난다.** 실제로 스모크가 `SE.ENABLED = True` 로 켠 줄
알았는데 안 켜져 있던 것이 상수를 없애면서 드러났다.

### 가져온 글이 그 기사가 맞는지 본다

뉴스 주소는 기사가 내려가면 다른 기사로 넘어간다. 실제로 이렇게 났다.

```
"CBAM 신고 의무, 무엇이 달라지나"  →  치약 세정제 기사
"EU CBAM 본시행 앞두고 준비 미흡"   →  AI 워크숍 기사
```

대조가 걸러 주긴 했지만, **우연히 관련 있는 글이 오면 그대로 근거가 된다.**
제목 낱말이 본문에 절반 이상 있어야 같은 기사로 본다 — 완전 일치는 못 본다.
사이트가 제목을 줄이거나 말머리를 붙인다.

걸러 내고 확인 목록에 올린다. **소재를 고른 근거였던 기사가 사라졌다**는
뜻이라 사람이 알아야 한다.

## 올리는 동안 상자가 진행을 보인다

PDF 하나에 30초 넘게 걸린다 — 글자를 뽑고, 어느 쪽을 쓸지 모델이 고른다.
그동안 아래쪽 한 줄뿐이면 **스크롤 밖일 때 아무 일도 안 일어나는 것처럼
보인다.** 상자 자체가 진행 화면이 된다.

## 소재 기사는 검색과 별개로 가져온다

주소를 이미 아는데 검색이 같은 URL 을 우연히 다시 찾기를 기다릴 이유가 없다.
예전에는 그래서 기사가 거의 늘 `fetch_failed` 로 남았다. 키 없이 도는
경로(`plain_fetch`)로 바로 가져온다 — 태그를 걷어 낸 글자만 쓰는 거친
방식이라 로그인·자바스크립트 페이지는 못 읽지만, **주소만 있고 못 쓰는
것보다는 낫다.**

### 검색이 없어도 돈다

`TAVILY_API_KEY` 가 없으면 명제만 나누고 전부 미확인으로 남는다. 지금까지의
"무엇을 어디서 확인할지" 와 같은 상태다. 명제를 못 나누면 옛 경로(`prompt.md`)로
되돌아간다. **중간이 실패해도 막지 않는다** — 근거 단계가 통째로 멈추면 사람이
할 수 있는 게 없다.

## 제목은 구조를 내용째 본다

제목을 구조 뒤로 옮겨 놓고도 **소제목 문자열만 넘기고 있었다.**

```
"달라지는 기준은 검증 가능성이다"
```

이 소제목만으로는 무엇이 검증되는지 — 법적 의무인지 내부 추적성인지,
공식 원문으로 확인된 것인지 — 알 수 없다. 구조를 앞에 둔 효과가 절반
사라진 상태였다.

지금은 `objective` · `covers` · `exclude` · `claim_refs` 를 함께 넘기고,
거기 걸린 **명제도 상태째** 넘긴다. 그래서 제목이 사실을 담을 때 그것이
확인된 것인지 안다.

| | 제목에서 |
|---|---|
| `supported` + `sufficient` | 확인된 사실이나 규정으로 쓴다 |
| `supported` + `insufficient` | 공식 의무처럼 쓰지 않는다 |
| `partial` | 확인된 범위를 넘는 단정을 안 쓴다 |
| `unverified` + `inference` | 제목의 사실 약속으로 안 쓴다 |

**제목 단계가 새 각도를 만들지 못하게** 했다. 각도는 이미 사람이 확정한
것이고, 후보는 **같은 글의 다른 표현**이지 다른 글이 아니다.

`title_style` 을 후보마다 다르게 강제하던 것도 뺐다. 구조에 셀 수 있는
목록이 없는데 숫자형을 만들면 뒤 단계가 그 수를 채우려 한다 — 오프라인
후보에 박혀 있던 `"대응 5단계"` 도 같은 이유로 없앴다.

### 모델에게 안 묻는 것 둘

**어떤 키워드가 제목에 들어갔는지**를 모델에게 물으면 제목에 없는 것을
썼다고 하거나, 입력에 없는 낱말을 지어내거나, 조사 때문에 빠뜨린다. 코드가
센다 — 공백을 접고 소문자로 맞춘 뒤 부분 문자열로 본다.

```
CBAM      → "CBAM이"      안에서 잡힌다
탄소 배출량 → "탄소배출량의"  안에서 잡힌다
가         → 한 글자는 안 센다
```

**대표 검색어**(`main_keyword`)도 검증한다. 모델이 고른 것이 제목에 실제로
없으면 버리고, 쓰인 키워드 중 검색량이 가장 높은 것으로 대신한다.

`click_reason` 은 만들고 버리던 값이라 없앴다. 슬러그는 길이뿐 아니라
**낱말 수**도 제한한다 — 길이만 자르면 마지막 낱말이 잘려 나간다.

## 유형은 제목 분류기가 아니다

프롬프트가 제목 낱말로 유형을 정하고 있었다.

| 제목 | 낱말이 가리킨 것 | 실제 |
|---|---|---|
| CBAM **적용** 대상은 무엇인가 | 케이스형 | 정보형 |
| LCI DB **구축** 방법 | 케이스형 | 가이드형 |
| 적용 여부 **확인** 방법 | 체크리스트형 | 가이드형일 수 있다 |

**`intent` 를 넘기는데 프롬프트가 안 봤다.** 각도 · 검색의도에 이어 세 번째
같은 문제였다 — 세 단계가 질문을 확정해 놓고 아무도 안 읽었다.

지금은 판단 순서가 박혀 있다.

```
question → desired_action → core_message → 유형별 필요 조건 → 제목 낱말(마지막)
```

`search_intent` 와 `article_type` 을 일대일로 대응시키지 않는다. 같은
`informational` 이라도 "무엇인가" 는 정보형이고 "무엇이 달라졌나" 는 동향형이다.
그래서 `ARTICLE_TYPES` 의 메타 문구에도 **검색의도 enum 을 안 적는다** —
적으면 프롬프트가 그것을 매핑표로 읽는다.

`unfit` 도 "추천하지 않음" 이 아니라 **그 유형으로 쓰면 글이 성립하지 않을
것**으로 다시 정의했다. 입력에서 부재를 확인할 수 있을 때만 담고, 애매하면
비운다. 그래서 소재를 `headline` · `summary` · `sources` 로 넘긴다 — 제목
한 줄로는 실제 사례가 있는지 알 수 없어 케이스형을 판단할 수 없다.

### 조용히 흐르던 두 곳

**모델이 낸 추천 이름을 검증하지 않았다.** `"동향"` · `"trend"` 가 오면 추천이
그냥 사라진다. 지금은 목록에 있는 것만 받고, 전부 부적합이면 통째로 지운다 —
고를 수 있는 유형이 하나도 없으면 사람이 화면에서 할 게 없다.

**`NAMES` 와 `skeletons.TYPES` 불일치를 코드가 안 막았다.** 주석에 "사람이
맞춰 둔 것" 이라고만 적혀 있었다. 어긋나면 구조 단계가 골격을 못 찾고 조용히
일반 구조로 흐른다 — 지금은 **뜨자마자 터진다.**

`type_reason` 도 확정값에 남긴다. 고르지 않은 유형의 이유는 지어내지 않는다.

## 검색의도는 분류가 아니라 질문이다

"후보마다 `search_intent` 가 달라야 한다" 를 요구했더니 **분류 체계가 질문을
지배했다.** 채널이 정보 탐색 단계라고 말하는데도 `commercial`(무엇을 기준으로
고를까) · `transactional`(누구에게 요청할까) 후보를 억지로 만든다 — 이 독자가
아직 하지 않는 질문이다.

순서를 뒤집었다.

```
소재 범위 → 독자의 문제 → reader_stage 에 맞는 것만
→ 답이 다른 질문 후보 → **그다음** 의도 분류
```

`search_intent` 가 같아도 답이 다르면 별도 후보다. 후보 수도 3~4개에서
**2~4개**로 — 수를 맞추려고 맞지 않는 질문을 넣지 않는다.

`sub_questions` 는 1~3개에서 **0~3개**로. 여기 적은 만큼 근거 단계가 검증할
범위가 넓어진다. `desired_action` 은 "행동" 만 요구하던 것을 **확인·판단·행동**
으로 넓혔다 — 단순 설명 글에 억지 행동이 붙던 자리다.

`rationale` 도 만들고 버리던 값이었다. 화면에만 쓰고 확정값에는 안 넣는다.

소재도 제목 한 줄이 아니라 `headline` · `summary` · `keywords` 로 넘기고,
**`fake.load_keywords()` 를 뗐다** — 소재 계약에 이미 있는 값을 가짜 데이터로
다시 가져오고 있었다.

## 각도는 판단 축이지 화자가 아니다

`viewpoint` 를 "누구 입장에서 쓰는가" 로 두었더니 후보가 이렇게 나왔다.

```
ESG 담당자가 준비할 일을 보는 시점
ESG 담당자가 내부 결재를 설득하는 시점
먼저 겪어 본 ESG 담당자 시점
```

**독자는 앞 단계에서 이미 정해졌다.** 여기서 또 정하니 화자의 상황만 바뀌고
글이 무엇을 중심에 놓는지는 안 달라진다. 지금은 이렇게 정의한다.

```
전환기간과 본격 시행의 공식 의무 차이를 기준으로 본다
기존 보고 자료의 재사용 가능성을 기준으로 본다
수출기업과 수입자의 정보 전달 관계에서 본다
```

**그리고 프롬프트가 `intent` 를 안 보고 있었다.** `build_input` 은 넘기는데
프롬프트에 그 낱말이 한 번도 안 나왔다 — 검색의도 단계를 만든 이유가
없어지는 자리다. 지금은 결정 우선순위를 명시한다.

```
question → sub_questions → reader 의 판단 → topic.summary 범위 → desired_action
```

`differentiation` 도 복구했다. 예전에는 프롬프트가 `rationale` 을 만들게 해
놓고 코드가 버렸다 — **모델에게 이유를 쓰게 하고 아무도 안 읽는 상태**였다.

`tone` 은 정확히 3개에서 1~3개로. 3개를 요구했더니 거의 모든 후보가
"실무적 · 차분한 · 근거중심" 으로 채워졌다. 톤은 채널 프롬프트와 브랜드
규칙이 다시 조절하므로 여기서는 핵심만 있으면 된다.

**여기는 근거 검증보다 앞이다.** `core_message` 는 이후 검증할 중심 논지이지
확인된 결론이 아니라서, 공식 원문이 손에 없는 상태에서 법적 의무·시행
요건·수치를 단정하지 않는다.

## 구조가 정하는 시각 요소는 셋이다

만드는 주체가 달라서 필드도 셋이다. 합치면 "이미지 세 장" 이 되어 파일
세 장을 약속하는 것처럼 보인다.

| | 무엇 | 누가 만드나 |
|---|---|---|
| `hero_image` | 글 전체를 상징하는 그림 | 생성 모델 (Gemini) |
| `sections[].image` | 내용을 이해시키는 **도식** | 코드가 마크업으로 (`figures.py`) |
| `sections[].illustration` | 상황을 보이는 **그림** | 생성 모델 |
| `sections[].media` | 실제 사진 · 자료 화면 | **사람이 파일을 넣는다** |

**`media.purpose` 는 그림의 존재 이유가 아니라 전달 내용이다.**

```
✗  공시 데이터 연결 방식을 구체화한다     ← 무슨 파일을 찾아야 할지 모른다
✓  같은 지표가 어느 시스템에서 왔는지 한 화면에서 확인되는 모습
```

`시각화한다` · `보조한다` · `구체화한다` 로 끝나면 코드가 버린다. 프롬프트로도
막고 코드도 본다 — 실제로 그렇게 나왔다.

**`media` 는 생성하지 않는다.** 회의 사진이나 공식 문서 화면을 모델이 그리면
그건 사진이 아니라 가짜 현장이고, 신뢰 요소가 정반대로 작동한다 — 작성자
이름을 안 지어내기로 한 것과 같은 이유다. 구조 단계는 "어떤 자료가 왜
필요한지" 까지만 정하고, 결과물에는 자리표시가 들어가며 발행 전 확인 목록에
"준비할 자료" 가 뜬다.

`media` 는 **네이버만 쓴다.** 규제 설명 글만 이어지면 블로그가 정보
데이터베이스처럼 보인다 — 실제 회사와 사람이 보이는 자리가 필요하다.
홈페이지는 구조화된 정보와 도식으로 설명하는 자리다.

필드는 두 채널 모두에 늘 둔다. 채널에 안 맞으면 **코드가 비운다** — 프롬프트에
"쓰지 마라" 를 적어 두어도 안 지키는 날이 있고, 모양이 채널마다 다르면
그것을 읽는 쪽이 양쪽을 다 알아야 한다. 제목의 `meta_description` · `tags` 와
같은 원칙이다.

**도식은 섹션을 다 만든 뒤에 판단한다.** 먼저 정하면 도식에 맞춰 섹션을
만들게 된다. `media` 도 마찬가지고, 대표 이미지가 제일 마지막이다.

## claim_refs — 구조가 정한 배치는 계약이다

구조 단계가 섹션마다 "이 섹션은 이 명제를 다룬다" 를 남긴다. 없으면 본문
작성이 소제목만 보고 근거를 다시 배치하고, **구조 단계가 한 판단이
사라진다.**

본문에는 **전체 명제를 다 넘긴다**(맥락을 잃지 않게). 다만 각 섹션의 핵심
주장과 인용은 그 섹션의 `claim_refs` 안에서만 고른다. 프롬프트로 막고
`write.check()` 가 한 번 더 막는다 — 벗어난 인용은 걸러 내고 발행 전 확인
목록에 남긴다.

`claim_refs` 가 빈 섹션(직접 쓴 구조가 그렇다)은 막지 않는다. 막으면 인용이
통째로 사라진다.

한 명제가 여러 섹션에 걸리는 것은 **허용한다.** 다만 역할이 달라야 한다 —
앞 섹션이 규정 내용을 설명했으면 뒤 섹션은 그 의미나 적용을 다룬다.

## 소재는 payload 이름이 두 벌이다

소재는 n8n·시트에서 오는 것이라 `topic_title` · `topic_summary` 로 들어오는데,
단계들은 `headline` · `summary` 를 읽고 있었다. **다섯 단계 전부에서 요약이
빈 문자열이었고 아무 오류도 안 났다** — 소재를 제목 한 줄에서 넓힌 작업이
통째로 무효였다.

`steps/payload.py` 의 `topic_brief()` 가 두 이름을 흡수한다. 같은 일을 다섯
곳에서 각자 하지 않고, 공급원이 바뀌면 여기만 고친다. 키워드도 소재 확정
시점에 payload 에 붙여 둔다 — 그래야 뒤 단계들이 소재 하나만 읽으면 된다.

## 유형 골격은 채우기 틀이 아니다

`for_outline()` 이 골격을 통째로 실었다 — 섹션 다섯 개가 제목과 covers 까지
적힌 채로. "참고자료" 라고 적어 두어도 그건 참고자료가 아니라 **채우기
틀**이고, 실제로 후보들이 전부 그 흐름으로 수렴했다. 허용된 변화가 "어디를
합치고 나눌까" 뿐이었다.

지금은 **무엇을 해내야 하는지**만 넘긴다.

```
purpose     이 유형이 독자에게 해 줘야 하는 것
must_have   빠지면 이 유형이 성립하지 않는 것
moves       자주 쓰는 전개 조각. 순서가 아니라 후보다
avoid       이 유형에서 하지 않는 것
```

`common.flow` · `common.section_count` 도 뺐다. 섹션 수는 채널 프롬프트가
이미 권하는데(홈페이지 4~7, 네이버 3~5) 공통이 "4~5개" 를 또 말하면 **채널
규칙이 무력해진다.**

같은 유형이라도 질문에 따라 구조가 달라야 하는 예도 프롬프트에 적었다.
비교형의 `moves` 는 둘 중 하나를 고르는 글의 전개인데, "기존 방식과 지금
필요한 방식은 무엇이 달라야 하는가" 는 **고를 대안이 둘 있는 것이 아니다.**
거기에 "A·B 설명" 과 "상황별 추천" 을 넣으면 없는 선택지를 만들게 된다.

## 채널을 가르면서 도식 스타일이 사라졌다

`figures.CSS` 를 싣는 곳이 **홈페이지 렌더러 하나뿐**이었다. 채널이 갈리면서
네이버 드래프트에는 홈페이지 결과물이 없으니, 네이버는 **마크업만 받고 규칙은
못 받았다.**

`class` 는 있는데 규칙이 없으니 브라우저 기본값으로 그려지고, 사람이 그걸
캡처해 블로그에 올렸다 — 구조도가 상자도 선도 없는 글자 목록으로, 대조표가
테두리 없는 맨 표로 나갔다.

지금은 네이버 결과물이 `figure_css` 를 함께 낸다. 화면이 `<style>` 로 싣고,
캡처는 `document.body` 에 붙으므로 그대로 따라온다.

**마크업이 한 벌이어도 스타일이 안 따라오면 소용없다.** 도식 데이터를 한 곳에
둔 이유가 두 채널이 어긋나지 않게 하려는 것이었는데, 스타일이 갈려서 결국
어긋났다.

## 도식은 본문보다 넓게 찍는다

본문 폭 680px 은 휴대폰에 맞지만 **4열 대조표에는 모자란다.** 실제 캡처에서
"우선 산 / 정", "남길 기 / 록" 처럼 낱말 가운데서 줄이 바뀌었다.

캡처본은 네이버 본문에서 화면 폭에 맞춰 줄어드니, **원본을 넓게 찍어도 최종
크기는 같다.** 형식마다 필요한 폭이 다르다.

```
항목카드 760 · 순서열 820 · 구조도 900 · 대조표 960
```

한국어는 `word-break: keep-all` 이 없으면 글자 단위로 줄이 바뀐다.
`table-layout: fixed` 도 같이 준다 — `auto` 로 두면 긴 셀이 열을 다 먹고
나머지가 짓눌린다.

**폭을 나누는 것만으로는 안 된다.** `.fig` 에 `max-width: 820px` 이 걸려
있어서, 상자를 960 으로 잡아도 **바깥 흰 여백만 늘고 표 열은 그대로
짓눌렸다.** 캡처 상자(`.bs-shot`) 안에서만 그 제한을 푼다. **id 가 아니라 class 다** —
한 번에 하나만 만들지만, 미리보기처럼 여러 개를 나란히 두면 문서에 같은 id 가
둘 생기고 `querySelector` 가 첫 것만 잡는다. 본문에서는 820 이
맞다 — 글줄이 길어지면 읽기 나쁘다.

## 유형이 답해야 할 것을 구조가 맡는다

**비교형인데 같은 기준이 없으면 비교가 아니다.** 유형을 골라 놓고 그 뼈대가
빠지면 글이 그 유형이 아니게 된다.

예전 `must_have` 는 `focus` 와 `question` 을 옮긴 것이라 추상적이었다 —
"동일한 기준에 따른 비교" 만으로는 무엇이 빠졌는지 사람도 코드도 알 수 없다.
지금은 **"무엇에 답해야 하는가"** 를 유형마다 넷 이상 든다.

```
비교형   무엇과 무엇을 견주는지 · 같은 기준이 무엇인지
        그 기준에서 무엇이 다른지 · 어느 쪽을 언제 고르는지
가이드형 언제 시작하는지 · 어떤 순서로 · 무엇이 필요한지 · 어떤 상태면 끝인지
```

구조가 `covers` 에 **어느 섹션이 맡는지** 적는다. 문구를 그대로 베끼라고
하지 않으므로 낱말 겹침으로 본다. 안 맡은 것이 있으면 카드와 확인 목록에
뜬다.

## 네이버 글은 끝이 있어야 한다

마지막 섹션이 목록이나 강조 박스로 끝나면 **글이 멈춘 것처럼 읽힌다.** 실제로
그렇게 났다 — 점검 항목을 늘어놓고 바로 안내 문구가 나왔다.

홈페이지는 참고자료 · 작성자 · 서비스가 뒤에 붙어 마무리가 되므로 안 본다.

## 견본 값이 남으면 최종본이 아니다

```
example.com · 김OO · 홍길동 · TODO · lorem ipsum
```

미리보기나 개발용으로 넣은 값이 그대로 나가면 회사 글에 남의 이름과 없는
주소가 실린다. 도식 · 사진 자리는 **사람이 채우는 것**이라 여기서 안 본다 —
그건 따로 알린다.

## 도식이 관계를 왜곡하는지 본다

**틀린 정보를 그림으로 확정하는 것**이 글로 쓰는 것보다 나쁘다. 글은 고칠 수
있지만 그림은 캡처해서 나가면 못 고친다.

실제로 이렇게 났다.

```
신고 의무
├─ 수입자              ← 의무 주체가 맞다
└─ 수출 제조기업        ← 자료를 대는 쪽인데 같은 자리에 있다
```

**이건 코드가 못 가른다.** 모양은 완전히 대칭이고, 두 갈래가 다른 층이라는
것은 뜻을 알아야 안다. 그래서 **프롬프트가 주된 방어**다 — 루트가 갈래를 다
포괄하는 말이어야 한다는 규칙과 이 예시를 박아 뒀다.

코드는 **모양으로 드러나는 것**만 잡는다.

```
갈래가 하나뿐        나누는 그림이 아니다
같은 이름이 위아래    계층이 아니다
깊이가 들쭉날쭉      같은 층으로 안 읽힌다
빈 열 · 중복 항목 · 단계 하나
```

막지 않는다. 확실히 못 가르는 것이라 사람이 봐야 한다.

## 구조도에 상하위를 잇는 선이 있다

선이 없으면 **상자 셋을 그냥 늘어놓은 것**으로 보인다. 순서열에는 세로선이
있는데(`.fig-steps::before`) 구조도에만 없었다.

세로 트리선으로 둔다. 흐름을 그려야 하면 그건 순서열이고, `direction` 같은
축을 새로 두지 않는다.

**세 선이 정확히 맞물려야 한다.** 좌표가 어긋나면 가운데에 짧은 꼬리가
보이거나 선이 끊겨 보인다.

```
루트 아래 10px  →  가로선  →  노드 위 10px
        (가지 margin-top 20px 의 가운데에서 만난다)
```

가로선은 **첫 가지 가운데에서 마지막 가지 가운데까지**만 그린다. 고정 %로
두면 가지 수가 바뀔 때 양끝에 꼬리가 남는다.

**`gap` 을 빼야 정확하다.** 노드 폭은 전체에서 여백을 뺀 나머지를 나눈
것이라, `50% / n` 만 쓰면 안쪽으로 들어간다 — 2가지 4px, 3가지 5.3px.
CSS 안에서는 `gap` 을 못 세므로 렌더러가 계산해 `--edge` 로 넘긴다.

```
n=2, gap=16  →  calc(25% - 4px)
n=3, gap=16  →  calc(16.6667% - 5.3333px)
```

가지가 하나면 잇는 것이 없어 안 그린다.

`:has()` 는 안 쓴다. 캡처 라이브러리가 못 읽을 수 있다.

**다만 루트에 도식 제목이 들어가고 있었다.** `"보고기업 기준 가치사슬"` 은
`caption` 이 할 말이다. 루트에 넣으면 "그 아래에 업스트림이 있다" 가 되어
**같은 것을 두 번 말한다.**

```
✗  root: "보고기업 기준 가치사슬"
✓  root: "보고기업"     caption: "보고기업을 기준으로 본 스코프3 가치사슬 구조"
```

`root` 를 읽고 `children` 을 읽었을 때 "◯◯ 아래에 △△가 있다" 로 말이
되어야 한다. 제목인지 대상인지는 코드가 확실히 못 가르므로 프롬프트가 막고,
코드는 **너무 긴 루트만** 자른다.

## 대조표는 입력이 두 모양으로 온다

모델이 `columns` 를 두 가지로 보낸다.

```
A. 비교 대상만     columns=[스코프1, 스코프2, 스코프3]        cells 3개
B. 기준 이름까지   columns=[판단 결과, 중요도, 조건, 기록]   cells 3개
```

**A 에서 `columns[0]` 을 기준 이름으로 쓰면 스코프1 자료가 통째로 사라지고
나머지가 한 칸씩 밀린다. B 에서 안 쓰면 이름이 하나 남아돌아 표가 밀린다.**
실제로 둘 다 겪었다 — B 를 고쳤더니 A 가 깨졌다.

**칸 수로 가른다.** 모양을 물어보는 것이 아니라 세는 것이라 확실하다.

```
cells == columns        A. 기준 열 이름이 없다 → "구분"
cells == columns - 1    B. columns[0] 이 기준 열 이름
```

행마다 칸 수가 다르면 가장 흔한 수를 따른다.

## 캡처할 때 구조도를 세로로 쌓지 않는다

항목카드는 한 줄로 세우는 것이 맞지만, 구조도를 그러면 **가지를 잇는
가로선이 붕 뜨고** 상하위 관계가 목록처럼 보인다.

그 규칙은 캡처 폭이 680 이던 때 만든 것이다. 지금 구조도는 900 으로 찍으니
두 갈래가 나란히 들어간다.

## 그림에 글자가 못 들어가게 코드가 막는다

프롬프트에 `no text` 규칙을 적어 뒀지만 **모델이 지시문에 안 넣으면
그만이다.** 실제로 `Existing reporting work` 가 철자까지 깨진 채 박혀
나왔다.

`gemini.draw()` 가 지시문 끝에 붙인다. 이미 있으면 두 번 안 붙인다.

```
no text, no letters, no words, no numbers, no labels, no captions,
no watermark. any documents or screens shown must be blank with no
writing on them
```

한글이든 영문이든 그림 안 글자는 **고칠 방법이 없다.** 도식을 마크업으로
그리는 것과 같은 이유다.

## 결과물 화면을 다시 받을 수 있다

본문 그림을 만들고 나면 화면이 그걸 받아야 하는데, **처음 한 번만 받으면
만든 그림이 계속 "아직 없음" 으로 남는다.** 파일은 만들어졌는데 화면에
안 떴다.

## 본문 그림은 여러 장이고 없어도 된다

대표 이미지와 흐름은 같지만(`llm.generate` → `gemini.draw` → 저장) 다른
것이 셋이다.

**하나가 실패해도 나머지는 쓴다.** 대표 이미지는 없으면 글이 허전할 뿐이지만
본문 그림은 **원래 없어도 되는 것**이라, 하나 때문에 나머지를 막을 이유가
없다. `POST /api/draft/illust` 는 일부만 실패해도 200 이고 `failed` 에 이유가
담긴다.

**섹션 번호로 잇는다.** 파일 이름이 `{sid}-s{order}.png` 다 — 본문의
`[본문 그림 삽입]` 이 어느 섹션인지와 같아야 사람이 어디에 넣을지 안다.

**이미 만든 것은 다시 안 만든다.** 나눠 부를 때마다 새로 그리면 사람이
저장해 둔 그림과 화면의 것이 달라진다.

글 한 편에 **두 장까지**다. 구조가 더 계획해도 코드가 자른다 — 그림이
많아지면 글이 아니라 화보가 되고 호출 수도 그만큼 는다.

## 같은 것을 두 가지로 보여주지 않는다

실제로 이렇게 났다.

```
media         거래처 요청 양식에서 배출량 범위를 확인하는 화면
illustration  담당자가 거래처 요청 문서에서 대상 범위를 찾아 표시하는 상황
```

둘 다 "요청 문서에서 범위를 확인한다" 다. 표현만 다르고 **독자는 같은 말을
두 번 본다.** 한 섹션에 도식이나 자료 화면이 있으면 그림을 안 넣는다 —
프롬프트가 막고 코드가 한 번 더 막는다.

```
실제 자료가 그렇게 생겼다는 것이 중요  →  media
그 상황이 어떤 것인지가 중요           →  illustration
관계·단계·비교가 중요                  →  image(도식)
```

## 대조표 첫 열은 기준의 이름이다

실제 결과물에서 표가 한 칸 밀렸다. 원인이 둘이었다.

**① 자르는 순서가 거꾸로였다.** 칸을 `len(cols)` 로 맞춘 **뒤에** `cols[:4]` 로
잘라서, 열이 다섯이면 헤더 넷에 본문 다섯 칸이 붙었다.

**② `columns[0]` 이 무엇인지가 어긋나 있었다.** 렌더는 `criterion` 앞에 빈
`<th>` 를 뒀는데, 모델은 그 자리 이름을 `columns[0]` 에 넣어 보낸다
("판단 결과"). 그러면 이름이 하나 남아돌고 표가 밀린다.

지금은 첫 열을 `criterion` 의 이름으로 쓴다(`head`). 열을 먼저 자르고 칸을
맞춘다.

## 같은 문서를 참고자료에 두 번 싣지 않는다

URL 만 보면 같은 문서의 **PDF 와 안내 페이지**가 둘로 남는다.

```
Corporate Value Chain (Scope 3) Accounting and ...   .../x.pdf
Corporate Value Chain (Scope 3) Standard             .../corporate-value-chain
```

도메인 + 제목 앞부분으로 가른다. 도메인이 다르면 다른 문서다 — 같은 제목의
다른 기관 자료를 하나로 접으면 안 된다.

## 추천은 다섯 단계에 붙는다

유형만 추천이 있었다. 나머지는 프롬프트에 "첫 번째를 ~로 두라" 가 있어도
**화면에 안 보였다** — 순서에 둔 뜻이 사라진 상태였다.

```
독자 · 검색의도 · 각도 · 유형 · 구조 · 제목
```

**첫 후보가 추천이다.** 후보마다 `recommended` 필드를 받지 않는다 — 모델이
여러 개를 추천하거나 하나도 안 하는 날이 있고, 그럼 코드가 또 정리해야 한다.
프롬프트가 이미 순서에 뜻을 두고 있으므로 그것을 쓴다.

**왜 추천인지를 함께 적는다.** "추천" 만 붙이면 그것만 고르고 나머지를 안
본다. 이유는 후보가 이미 들고 있는 값을 쓴다 — 각도는 `differentiation`,
검색의도·구조·제목은 `rationale`, 유형은 `type_reason`. 새로 지어내지 않는다.

```
추천 · 내부 대응 방법보다 제도가 정한 변화를 먼저 짚는다 · 톤 정확한 / 실무적
```

**근거에는 안 붙인다.** 여러 개를 고르는 유일한 단계라, 추천이 붙으면 그것만
고르고 나머지를 안 본다. 근거는 나란히 놓고 견주는 자리이고, 이미 상태
표시(`확인됨 · 공식 근거 · 출처 2건`)가 판단 재료다.

소재와 채널에도 안 붙인다. 소재는 이미 점수로 줄 세워져 있고, 채널은 둘뿐이라
사람이 정할 일이다.

**화면은 메타 글자로 알아본다.** 규칙을 두 곳에 두지 않는다.

## 추상 명사는 무엇인지 함께 적는다

`의무 구간` · `요청 형식` · `관련 자료` 같은 말은 그 자체로는 아무것도 안
알려 준다.

```
✗  거래처가 어느 의무 구간에 있는지, 우리 자료가 요청 형식과 맞는지
✓  거래처의 수입량이 기준을 넘는지, 요청 양식에 CN 코드·설비 정보·보고기간이
   포함되는지
```

**`vague()` 는 이걸 통과시킨다** — `자료`·`형식` 이 표시로 잡히기 때문이다.
표시는 있는데 **그 표시가 가리키는 것이 안 풀린** 경우라 따로 본다.

항목을 늘어놓는 것이 곧 무엇인지 적는 것이다. 나열이 있으면 푼 것으로 본다.

두 검사가 겹치면 `vague` 가 먼저다 — 표시조차 없는 쪽이 더 나쁘다.

## 도식과 본문 그림의 역할이 갈린다

실제로 그림과 도식이 둘 다 "무엇이 달라졌나" 를 설명했다.

```
도식        제도가 어떻게 갈리는가 — 관계 · 순서 · 비교
본문 그림    사람이 처한 상황 — 어느 부서 자료가 어디로 가는가
자료 화면    실제 자료가 그렇게 생겼다는 것
```

같은 섹션이 아니어도 **역할이 겹치면 정보 밀도가 떨어진다.**

## 대조표 행마다 다른 것을 잰다

```
✗  신고 주기   분기별 보고      연간 신고
   일정 관리   분기 단위 마감    연간 단위 마감      ← 같은 말이다
```

**행끼리 같은 말을 하는지는 코드가 못 가른다.** 낱말 겹침으로 보면 정상인
표("보고 신고자" vs "분기별 보고")가 더 높게 나온다. 프롬프트가 막는다.

**한 행의 칸이 같은 축인지**는 코드가 본다. 왼쪽이 주체 이름인데 오른쪽이
해야 할 행동이면 나란히 놓아도 견준 것이 아니다.

```
✗  자격 범위   보고 신고자 기준   거래 조건별 적용 확인
```

## 참고자료에 기관명이 앞에 온다

문서 제목만 있으면 **그것이 공식 자료인지 민간 해설인지 구분되지 않는다.**
`official_primary` 같은 내부 이름을 그대로 내보내면 사람에게 아무 뜻이 없다.

```
DEHSt                 CBAM Certificates
European Commission   Carbon Border Adjustment Mechanism
taxnews.ey.com        European Commission sets conditions
```

모르는 곳은 도메인을 보인다 — 어디서 왔는지는 알 수 있다.

## 도식이 본문보다 앞서지 않는다

본문이 셋을 짚는데 도식에 다섯이 들어가면, **읽는 사람은 나머지 둘을 어디서
확인해야 할지 모른다.**

```
본문   신고 주기 · 업무 주체 · 내재배출량과 인증서
✗ 도식  신고 주기 · 업무 주체 · 내재배출량 · 일정 관리 · 자격 범위
```

기준의 낱말이 본문에 있는지로 본다. 겹침 비율로 보면 **본문이 길수록 늘
낮게 나와서 전부 걸린다.**

## 출처를 뭉뚱그리지 않는다

`관련 보도에서` · `업계에서는` 은 어디를 봐야 하는지 안 알려 준다.
**출처를 흐리게 적는 것은 없는 근거를 있는 것처럼 보이게 한다.**

인용할 자료가 있으면 `cites` 로 달고, 없으면 그 문장을 안 쓴다.

## 참고자료 제목을 다듬는다

검색 결과 제목을 그대로 쓰면 **잘린 티가 난다.**

```
✗  European Commission sets conditions and procedures for authorized ...
✗  DEHSt  -  CBAM Certificates
✓  European Commission sets conditions and procedures for authorized
✓  DEHSt - CBAM Certificates
```

**잘린 뒤를 만들어 내지는 않는다** — 없는 제목을 지어내는 것이 더 나쁘다.
말줄임표만 떼고 구분자를 정리한다.

## 참고자료에 본 쪽을 적는다

문서명만 있으면 읽는 사람이 **그 문서 어디를 보라는 것인지** 알 수 없다.

```
✗  EU_CBAM_본격시행_대응가이드_2026
✓  EU_CBAM_본격시행_대응가이드_2026 — 첨부 문서 2·4쪽
```

대조가 인용마다 남긴 `location` 에서 쪽을 뽑는다. 웹 원문은 절 제목이라
쪽이 아니므로 안 붙는다.

## 구조 문제와 근거 문제를 갈라 적는다

한 줄에 섞으면 **구조를 바꿔야 하는지 근거를 더 찾아야 하는지** 사람이
구분할 수 없다. 근거가 모자란 것은 구조를 바꿔도 안 풀린다.

```
구성 점검: 정보형에 필요한 내용 5가지 부족, 절차 중심 부분이 3개 연속
근거 점검: 확인된 근거 현재 2 / 기준 4
```

`2→4` 같은 계산 표기는 안 쓴다. "현재 2 / 기준 4" 가 무엇을 뜻하는지
바로 읽힌다.

**펼치면 무엇이 빠졌는지 보인다.** 개수만으로는 이 구조를 고를지 판단할 수
없다.

```
빠진 내용 — 무엇인지 정의 · 어디에 적용되는지 · 무엇으로 이루어졌는지
```

## 요약 줄 표시는 한 모양이다

`+도식` · `+그림` · `자료 1장` 처럼 섞으면 내부 표기처럼 보인다.

```
품목과 설비를 먼저 식별한다
→ 생산량과 배출량을 잇는다 [도식]
→ 무엇을 묶어 보내나 [자료 화면]
→ 정리
```

## 화면에 내부 계약명을 보이지 않는다

`covers` · `claims` · `authority` · `partial` 은 파이프라인 안에서 쓰는
이름이다. **사람은 그 뜻을 알 이유가 없다.**

실제로 구조 카드에 이렇게 나갔다.

```
✗  섹션 3/4 · covers 5/8 · 명제 2/4 · 유형 필수 1건 안 다룸
✓  3개 부분 · 모자람: 부분 3→4, 다루는 내용 5→8, 확인된 근거 2→4
   · 정보형에 필요한 내용 1가지 빠짐
```

바꾼 자리는 넷이다.

```
근거 카드 kind    명제 → 확인 대상
자격 라벨         출처 자격 부족 → 공식 근거 부족
구조 카드         섹션·covers·명제 → 부분·다루는 내용·확인된 근거
확인 목록         쓴 명제 → 반영한 근거
```

**내부 이름은 코드와 로그에만 둔다.** 로그는 `claim_id` · `authority` ·
`reason_code` 를 그대로 남긴다 — 디버깅이 그 이름으로 이뤄지기 때문이다.

## 홈페이지는 네이버를 늘린 것이 아니다

같은 근거를 쓰더라도 홈페이지는 **한 층 더 들어간 설명**을 담는다. 문장을
늘리거나 서비스·안내만 붙이면 네이버 본문에 CTA 만 얹은 꼴이 된다.

```
왜 기존 자료로 대체할 수 없는지
어떤 조건에서 달라지는지
언제 무엇이 더 필요한지
내부에서 무엇을 이어야 하는지
판단이 갈리는 기준과 예외
```

**전부 넣으라고 하지 않는다.** 근거가 없는 것을 이 목록 때문에 만들어 내면
그게 더 나쁘다. 해당하는 것이 하나뿐이면 하나만 쓴다.

## 조사를 목록 뒤에 이어 붙이지 않는다

앞말 받침에 따라 이/가가 달라지는데 목록 끝이 무엇일지 모른다.

```
✗  메타 설명 · URL 슬러그이 비어 있습니다
✓  비어 있습니다 — 메타 설명 · URL 슬러그
```

## 흐름은 근거가 정한다

**같은 소재라도 질문이 다르면 흐름이 달라야 한다.** 책임을 물으면 주체 중심,
준비 자료를 물으면 데이터 흐름, 적용 대상을 물으면 기준·예외 흐름이다.

그런데 유형 골격이 앞에 있으면 무엇을 물어도 비슷하게 접힌다.

```
상황 제시 → 개념·주체 설명 → 항목 목록 → 먼저 확인할 것 → 요약
```

`evidence_shape` 가 **확인된 명제가 어느 쪽으로 쏠려 있는지**를 한 줄로
넘긴다. 주체·책임 · 기준·예외 · 절차·순서 · 변화·시점 · 비교·차이 ·
자료·산정 · 일정·기한 · 위험·누락 여덟 갈래다.

**분류기가 아니라 요약이다.** 이 값으로 구조를 정하지 않는다 — 모델에
"지금 근거가 이런 쪽이다" 를 알려 주고 흐름은 모델이 정한다. 프롬프트에
갈래별 흐름 예시를 주되 **그것도 순서가 아니라 예시**라고 못 박는다.

`skeletons` 는 **구조를 만드는 틀이 아니라 빠진 것을 검사하는 자**다.
`must_have` 는 사후 검사고, `moves` 는 조각이지 순서가 아니다.

## 후보끼리 설명 흐름이 달라야 한다

근거 배치가 달라도 `상황 → 기준 → 정리` 가 되풀이되면 **독자가 이해하는
경로는 같다.** 지문에 `role` 순서를 넣어 그것도 본다.

```
1번 후보와 근거 배치가 같음     소제목만 다른 후보
2번 후보와 설명 흐름이 같음     배치는 다른데 경로가 같은 후보
```

지우지 않는다. 그 흐름이 맞는 소재도 있다.

## 근거가 있는데 일찍 끝내지 않는다

근거 문서에 열 묶음이 있는데 셋만 쓰고 900자로 끝난 글이 나왔다. **질문에
답하기 전에 끝난 것**이다.

**글자 수만 세면 반복이 는다.** 같은 말을 늘려 써도 하한을 넘기 때문이다.
넷을 함께 본다.

```
섹션 수 · 서로 다른 내용(covers) · 쓴 명제 수 · 본문 글자 수
```

유형이 기본을 정하고 채널이 보정한다. 홈페이지는 정의·근거·해석·서비스
연결까지 담으므로 섹션 1 · 내용 2 · 명제 1 을 더 들고 글자는 25% 위다.

```
네이버 정보형    섹션 4 · 내용 8  · 명제 4 · 1,600~2,400자
홈페이지 정보형   섹션 5 · 내용 10 · 명제 5 · 2,000~3,000자
```

**같은 것을 표현만 바꿔 두 번 쓰면 하나로 센다.** "무엇인지 정의" 와
"정의가 무엇인지" 는 같은 내용이다. 낱말 겹침으로 접는다 — 명제를 가르는
것과 같은 방식이고, `sanitize.stems` 한 곳에 둔다.

**도식 안 글자는 안 센다.** 표 하나로 하한을 넘길 수 있다.

구조 카드에 `섹션 3/4 내용 5/8 명제 2/4` 로 뜬다. **고르기 전에 보인다.**

## 무엇을 하라고 할 때는 무엇을 보라고까지 쓴다

**"확인합니다" 로 끝나는 문장은 아무것도 안 알려 준다.** 독자는 이미
확인해야 한다는 걸 알고 있고, **무엇을 어떤 기준으로** 보는지를 모른다.

```
✗  원천 데이터를 확인합니다
✓  그 수치가 어느 시스템에서 추출됐고, 보고기간과 조직경계가 무엇인지 확인합니다

✗  담당 부서를 정해 관리해야 합니다
✓  산정 담당과 승인 담당을 나누고, 어느 자료까지 누가 책임지는지 정합니다
```

확인·점검·관리·연결·구분·검토·정리·비교 같은 말이 들어간 문장에는 대상 ·
출처 · 기간 · 범위 · 단위 · 주체 · 완료 조건 · 예외 중 **둘 이상**이 있어야
한다.

**사실을 설명하는 문장은 안 본다.** "전환기간에는 분기별 보고가 적용됩니다"
는 무엇을 하라는 말이 아니므로 짧아도 된다. **행동을 권하는 문장에만** 붙는
규칙이다.

**행동 동사가 붙은 말은 표시로 안 센다.** "담당 부서를 정해 관리한다" 의
`담당` 은 무엇을 볼지 알려 주는 것이 아니라 행동 그 자체다.

프롬프트가 막고 코드가 센다. 문단 · 목록 · 체크 · 강조 · 도식 해석을 다 보고,
모자란 문장을 발행 전 확인 목록에 올린다. 막지는 않는다 — 어느 문장을 손볼지
알려 주는 것까지다.

## 논리가 이어지는 것과 리듬이 사는 것은 다르다

실제로 나온 글이 이랬다.

```
섹션1  설명 → 번호형 목록 → 정리
섹션2  설명 → 도식
섹션3  설명 → 번호형 목록 → 정리
섹션4  설명 → 번호형 목록 → 강조
```

순서는 맞는데 **같은 리듬이 세 번 되풀이된다.** 본문 프롬프트에 "`list` 다음에
바로 `list` 를 놓지 않습니다" 가 있었지만 그건 **한 섹션 안의 규칙**이라,
섹션을 건너뛴 반복은 아무도 안 봤다.

두 층에서 막는다.

**구조가 `role` 을 정한다.** 상황 · 원인 · 구조 · 비교 · 절차 · 기준 · 정리
일곱 중 하나. 같은 역할이 **연속으로 셋 이상**이면 카드에 표시한다. 떨어져
있는 반복은 막지 않는다 — 상황·비교·상황 은 정당하다.

**본문은 코드가 센다.** 섹션이 무엇으로 끝나는지(`shape_of`) 보고 셋이
연달아 같으면 발행 전 확인 목록에 뜬다. 프롬프트로만 막았더니 안 지켜졌다.

막지 않는 이유는 이미 만들어진 본문을 코드가 다시 쓸 수 없고, 정당한 경우도
있어서다. **어디를 볼지 알려 주는 것까지가 코드 몫이다.**

## 도식을 "굳이 필요한가" 로 묻지 않는다

판단 순서가 마지막이라(섹션을 다 만든 뒤) 이미 만든 것에 나중에 붙이게 되고,
그러면 **"이건 굳이 없어도 되겠다" 로 기운다.** 섹션 넷짜리 글에 도식이
하나만 나온 이유다. `media` 가 전부 `null` 이던 것과 같은 편향이다.

묻는 방식을 바꿨다.

```
✗  이 섹션에 도식이 필요한가
✓  이 섹션을 줄글로만 설명하면 독자가 머릿속에 그림을 그려야 하는가
```

**그래도 수는 안 채운다.** 최소 개수를 못 박으면 없는 도식을 만들고, 그건
본문과 같은 말을 반복한다. 대신 도식이 하나 이하면 확인 목록에 뜬다.

## 첫 후보가 추천이다

프롬프트가 이미 "가장 맞는 것을 첫 번째로" 라고 정해 두었는데 **화면에는 안
보였다.** 유형만 추천 표시가 있었다.

다섯 단계에 붙였다 — 독자 · 검색의도 · 각도 · 구조 · 제목.

```
추천 · 요청을 받은 직후에 가장 먼저 막히는 지점이다 · 절차 확인 · 읽고 나서 ~
```

**왜 추천인지가 없으면 추천이 아니다.** 그냥 첫 번째라는 뜻이 되고 사람은
그걸로 판단할 수 없다. 이유는 각 단계가 이미 들고 있다 — 각도는
`differentiation`, 검색의도·구조·제목은 `rationale`, 유형은 `type_reason`.

**이유는 한 번만 보인다.** 말머리에 넣고 메타 끝에도 두면 같은 문장이
한 줄에 두 번 나온다 — 실제로 검색의도에서 그렇게 났다.

### 붙이지 않은 자리

| | 왜 |
|---|---|
| 소재 | 이미 점수로 줄 세워져 있다 |
| 채널 | 둘뿐이고 사람이 정할 일 |
| **근거** | **여러 개 고르는 자리**다. 하나에 추천이 붙으면 그것만 고르고 나머지를 안 본다 |

근거에는 대신 상태가 붙는다(`확인됨 · 공식 근거 · 출처 2건`). 그게 판단
재료다.

## 후보는 전략이 달라야 한다

"어디를 합치고 나눴는지" 만 다르면 같은 후보다. 셋 중 **둘 이상**이 달라야
한다.

```
첫 핵심 섹션이 답하는 문제 · claims 를 묶는 기준 · 섹션의 논리적 순서
```

**같은 명제를 여러 핵심 섹션이 맡지 않는다.** 그러면 소제목만 다르고 같은
설명이 반복된다. 결론 섹션의 `claim_refs` 는 비운다 — 결론은 앞이 남긴 것을
모으는 자리지 명제를 새로 맡는 자리가 아니다. 겹치면 카드에 표시한다(지우지는
않는다. 앞이 사실을, 뒤가 그 적용을 다루는 것은 정당하다).

## 구조 단계가 명제를 상태째 본다

예전에는 근거를 `{title, kind, confirmed}` 로 접어 넘겼다. 그러면 **"원문과
어긋남"(`contradicted`)과 "아직 못 찾음"(`unverified`)이 같은 값**이 된다 —
앞은 쓰면 안 되는 것이고 뒤는 조건을 붙여 쓸 수 있는 것이다. `claim_id` 도
버려서 `claim_refs` 를 만들 수가 없었다.

지금은 `claim_id` · `claim_type` · `status` · `authority` · `limitations` 를
그대로 넘긴다. 인용문과 URL 만 뺀다 — 그건 본문이 확정값에서 다시 읽는다.

소재도 제목 한 줄이 아니라 `headline` · `summary` · `keywords` 로 넘긴다.
같은 제목이라도 요약과 키워드가 다르면 다뤄야 할 것이 다르다.

## type_structure 는 명령이 아니라 안전망이다

고정 규칙 셋이 겹쳐서 사실상 틀로 작동하고 있었다.

```
flow 의 순서를 뒤집지 않는다
focus 구간은 반드시 남긴다
도입 1 + 핵심 3 + 결론 1, 전체 4~5개가 기본
```

채널 프롬프트가 `4~7` · `3~5` 를 권하는데 공통이 `4~5` 를 박아 놔서 **채널
규칙이 무력화됐다.** 셋 다 완화하고 우선순위를 명시했다.

```
question → claims → core_message → reader → article_type → type_structure
```

`type_structure` 는 **앞의 다섯을 만족한 뒤 참고하는 안전망**이고, 부딪히면
`question` 과 `claims` 를 따른다.

**도식은 섹션을 다 만든 뒤에 판단한다.** 먼저 생각하면 도식에 맞춰 섹션을
만들게 된다. "본문 도식 2개가 기본" 도 뺐다 — 수를 정해 두면 그 수를 채운다.

후보끼리 다른지도 `claim_refs` 로 잰다. 근거 배치가 같으면 소제목만 다른
후보다. **지우지 않고 표시한다** — 지웠다가 후보가 하나만 남으면 화면이 막힌다.

## 구조가 평면적이면 발행 전에 알린다

구조 카드에 이미 표시하지만 사람이 안 보고 넘어갈 수 있다. 발행 전 확인
목록이 한 번 더 짚는다.

```
근거 배치    같은 근거를 여러 섹션이 다룹니다
마지막 섹션  마지막 섹션이 근거를 여러 개 다시 듭니다
```

**막지는 않는다.** 이미 고른 뒤라 되돌릴 수 없고, 결과물을 읽기 전에 어디를
볼지 알려 주는 것까지가 코드 몫이다.

## 근거가 없으면 그것이 결과물에 드러난다

인용할 수 있는 근거가 0건인데 **최종 글이 발행 가능한 완성본처럼** 나오던
자리다. 세 곳에서 막는다.

**본문이 안다.** `evidence_state.can_assert` 를 넘긴다. 빈 목록만으로는
모델이 "안 준 것" 과 "없는 것" 을 구별 못 하고, 실제로 빈 자리를 스스로
정의로 메웠다 — "공시 데이터 체계는 ~하는 구조입니다" 가 입력 어디에도 없이
나왔다. 근거가 없다는 것은 "네가 아는 것으로 채우라" 가 아니라 **"이 글은
아직 사실을 단정할 수 없다"** 는 뜻이다.

**`claim_refs` 가 빈 섹션이 그 자리다.** 근거를 안 걸어 둔 섹션이라 모델이
"내가 채워야 하는 자리" 로 읽는다. 쓸 수 있는 것을 셋으로 못 박았다 —
앞을 잇는 문장, 독자가 겪는 상황, 다음으로 넘어가는 안내. **정의로 시작하지
않는다.**

**제목이 약속을 낮춘다.** 근거가 없으면 "왜 ~인가" · "~의 핵심" · "~하는
3가지" 를 쓰지 않는다. 본문이 그 답을 못 주는데 제목이 약속하면 그 제목이
틀린 것이다. 다만 **문자열을 자동으로 치환하지 않는다** — 그러면 제목이
망가진다. 프롬프트가 판단한다.

**발행 가능 상태를 한 줄로 준다.** 확인 목록이 길면 사람이 안 읽고 발행하는
것이 실제 실패였다. 결과물 맨 위에 뜬다.

```
발행 전에 확인할 것이 1건 있습니다
  본문에 출처를 달 수 있는 근거가 하나도 없습니다      명제 3건 중 인용 가능 0건
```

막지는 않는다. 근거 없이도 내야 할 때가 있고 그 판단은 사람 몫이다.

## 네이버 서식은 백엔드가 붙인다

네이버 에디터는 class 를 지우므로 style 을 인라인으로 넣는다. 그 인라인을
**화면이 붙이고 있었다.**

```js
box.querySelectorAll('blockquote').forEach(el => {
  el.style.borderLeft = '3px solid #ddd';    // 브랜드 색이 아니다
});
```

태그 종류만 보고 칠하니 **소제목·리드·도식 자리를 구별하지 못했다.** 소제목과
본문이 둘 다 `margin: 0 0 14px` 라 스크롤할 때 섹션이 어디서 시작하는지 안
보였고, 강조 박스가 회색으로 나갔다.

지금은 `brand.NAVER` 가 값을 들고 렌더러가 붙인다. 화면은 화면 전용 요소를
걷어 내기만 한다.

| | 전 | 후 |
|---|---|---|
| 소제목 | `0 0 14px` · 본문과 같음 | `32px 0 10px` · 네이비 |
| 리드 | 본문과 같음 | `17px` · 위아래 넉넉히. **박스로 안 감싼다** |
| 본문 | `0 0 14px` · **line-height 없음** | `0 0 18px` · `1.9` |
| 목록 항목 | `0 0 8px` | `0 0 14px` · 제목에 네이비 |
| 강조 박스 | `#ddd` 회색 | 브랜드 파랑 + 옅은 배경 |
| 그림 자리 | `━━━` 위아래 두 줄 | 점선 상자 하나 |
| 대표 이미지 | 파일명(`f9d0c2...png`) | 무엇을 넣을 자리인지 |

**리드를 박스로 안 감싸는 이유**는 그게 본문 진입부라서다. 감싸면 안내·요약처럼
보여서 본문이 아직 시작 안 한 것으로 읽힌다. 박스는 그림 자리와 강조에만 쓴다 —
세 종류가 되면 뭐가 중요한지 안 보인다.

**구분선으로 그림 자리를 감싸지 않는 이유**는 그림을 넣고 나서도 줄이 남기
때문이다. 점선 상자는 그림으로 바꾸면 상자째 사라진다. **실선으로 안 바꾸는
이유**도 같다 — 실선은 완성된 정보 박스로 보이는데, 거기는 아직 비어 있고
사람이 채워야 하는 자리다.

**본문에 `line-height` 를 반드시 준다.** 안 주면 에디터 기본(1.5~1.6)이
먹어서 글에서 제일 많은 자리만 빽빽해진다 — 리드·목록·강조는 다 1.8~1.9 인데
본문만 빠져 있었다.

**강조 박스의 라벨과 본문은 각각 `<p>` 다.** `display:block` 에 기대면
에디터가 그것을 지웠을 때 "실무 포인트여러 채널에…" 로 붙는다.

**CTA 가 없으면 구분선도 안 나간다.** 글이 선 하나로 끝나면 마무리가 아니라
잘린 것으로 보인다. 서비스가 없다는 사실은 발행 전 확인 목록에만 있다 —
독자가 볼 글에 우리 내부 상태를 쓰지 않는다.

## 붙여넣기 결과를 확언하지 않는다

"굵기·목록·인용이 그대로 따라갑니다" 는 지킬 수 없는 약속이다. 네이버는
외부 글을 그대로 붙여넣는 것을 권장하지 않고, 브라우저와 에디터 상태에 따라
결과가 다르다. **안 따라왔을 때 사람이 자기가 잘못한 줄 안다.**

대신 **붙여넣은 뒤 손볼 것**을 목록으로 준다(`naver.recipe`).

```
도입        가운데 정렬 · 인용구        첫 화면에서 눈이 멈추는 자리다
소제목      한 단계 큰 크기 · 굵게      3개. 스크롤로 읽으므로 구간이 보여야 한다
강조 문단    인용구 서식               2곳. 굵게만 하면 본문과 안 갈린다
```

**본문 데이터에 정렬·간격을 넣지 않는다.** 넣어도 붙여넣기에서 대부분 안
살아남고, 모델이 문단마다 정하면 장식이 과해진다. 본문 모양을 코드가 읽어서
안내만 만든다.

## 참고자료는 실제로 인용한 것만

`sources` 는 프롬프트에 **넘긴** 목록이라 안 쓴 것도 들어 있다. 그것까지
실으면 읽어 보지도 않은 자료가 출처로 나가고, 그건 "출처가 있다" 를 흉내
내는 것이다. 섹션의 `cites` 에 남은 id 로 거른다.

## 규정과 권고를 문단으로 가른다

결과물이 이렇게 나온 적이 있다 — 제목은 "무엇이 바뀌나" 인데 본문은 제품
코드 연결, 자료 보관, 담당자 지정 같은 **내부 관리 조언**으로 채워졌다.
실무적으로 쓸모는 있지만 규정이 정한 변화가 아니다.

그래서 본문 규칙을 둘로 나눴다.

**표현의 강도는 `authority` 가 정한다.**

| `claim_type` · `authority` | 문장 |
|---|---|
| `regulation` · `sufficient` | 규정이 ~를 요구합니다 |
| `regulation` · `insufficient` | 보도에서는 ~라고 설명합니다 |
| `interpretation` | 이는 실무에서 ~를 뜻합니다 |
| `inference` | ~할 수 있습니다 |

**공식적으로 달라진 것과 실무적 의미를 한 문단에 넣지 않는다.** 먼저 제도가
정한 변화를 쓰고, 그다음 **별도 문단**에서 그것이 실무에서 무엇을 뜻하는지
쓴다. 섞으면 회사가 만든 권고가 법적 의무처럼 읽힌다.

**코드는 문장을 못 읽는다.** 프롬프트로 막았지만 지켰는지는 사람이 봐야 안다.
그래서 자격이 모자란 출처로 규정·사실을 서술하면 발행 전 확인 목록에
"출처 자격" 이 뜬다. 막지는 않는다 — 막으면 근거 없는 글이 나온다.

## 근거를 두 종류로 다르게 다룬다

근거 단계 프롬프트는 검색을 하지 않고 URL 을 금지한다. 그래서 확정된 근거 중
**URL 이 있는 것은 소재에 딸려온 기사뿐**이고, 나머지는 "무엇을 어디서
확인할지"까지만 정해진 미확인 대상이다.

| | 확인된 출처 | 미확인 근거 |
|---|---|---|
| 본문에서 | 인용하고 매체를 언급한다 | 사실로 단정하지 않는다 |
| 참고자료 | 링크로 나간다 | **나가지 않는다** |
| 어디로 | 결과물 | 발행 전 확인 목록(`checklist`) |

미확인 근거를 참고자료에 실으면 확인되지 않은 것에 출처가 붙은 글이 된다.
이건 이 파이프라인에서 반복해 나온 실패라 **프롬프트와 코드 양쪽에서 막는다** —
`write.md` 가 금지하고, `write.check()` 가 `cites` 에서 걸러낸다. 한 겹으로
두기엔 위험하다.

## 근거로 쓸 PDF 를 올린다

근거 단계 프롬프트는 검색을 하지 않는다. 그래서 URL 이 붙은 확인된 출처는 소재에
딸려온 기사뿐이고, 나머지는 "무엇을 어디서 확인할지" 까지만 정해진 대상이다.
**사람이 원문 PDF 를 직접 올리면 그 자리가 메워진다.**

| | 확인된 출처 | 미확인 근거 |
|---|---|---|
| 무엇 | 소재에 딸려온 기사(`url`) · 사람이 올린 PDF(`file`) | 나머지 |
| 본문에서 | 인용하고 출처를 언급한다 | 사실로 단정하지 않는다 |
| 참고자료 | 기사는 링크로, 문서는 이름으로 | 나가지 않는다 |

**올린 문서는 확인된 출처다.** 원문을 손에 쥐고 올린 것이라 기사보다 확실하다.
다만 URL 이 없으므로 참고자료에는 링크가 아니라 문서명으로 나간다.

"확인된 출처인가" 를 묻는 곳이 둘이다 — 근거 단계 확정 라벨과 본문 작성의 근거
가르기. **따로 적었더니 곧바로 어긋났다.** 라벨은 `url` 만 보고 본문은
`url`·`file` 을 봐서, 올린 PDF 가 인용은 되는데 라벨에는 "확인 필요" 로
세어졌다. 지금은 `steps/payload.py` 의 `is_confirmed()` 한 곳이 정하고 `test.py`
가 둘이 같은 답을 내는지 검사한다.

**파일명만 받으면 근거가 아니라 장식이다.** 본문 작성이 그 안을 봐야 인용할 수
있으므로 올리는 순간 글자를 뽑아 둔다(`pypdf`). 쪽별로 뽑아 두는데, 긴 문서에서는
어느 쪽을 쓸지 골라야 하고 이어 붙인 뒤에는 되돌릴 수 없기 때문이다.

### 앞에서부터 자르면 안 된다

58쪽 EU 이행규정으로 재 봤다. 앞 6,000자에 들어간 것은 표지와 목차와 전문
아홉 개뿐이었고, 인용할 조항 — 보고 의무, 요구 정보, 검증 요건 — 은 14,812자
·15,106자·30,116자 지점에 있어 하나도 안 들어갔다. 길어서 아쉬운 게 아니라
**가장 쓸모없는 구간을 골라 보내고 있었다.**

그러면 두 가지가 무너진다.

1. 근거 단계 프롬프트가 문서를 헛본다. 아는 것이 표지 문구뿐이라 "이미 올린 것과
   겹치지 마라" 를 판단할 수 없고, 방금 올린 규정을 다시 "규정 원문에서 확인할
   것" 으로 내놓는다.
2. 카드에는 "출처 확인됨" 이 뜨는데 넘어간 것은 전문뿐이다. 모델이 표지 문구로
   그럴듯한 문장을 지으면 **확인된 출처로 표시된 채** 나간다.

그래서 `pick.py` 가 쪽별 앞머리만 모아 한 번 물어보고 쪽 번호를 받는다.
키워드로 코드가 맞추는 방식은 이 도메인에서 못 쓴다 — 글은 한글로 쓰고 근거는
영문 규정인 경우가 흔해 겹치는 낱말이 거의 없다.

**한도 안에 들어가는 문서는 물어보지 않는다.** 첨부 대부분은 몇 쪽짜리 고시나
가이드라 그대로 통과한다. 호출은 긴 문서에만 든다.

고른 쪽은 `[25쪽]` 처럼 번호를 박아 이어 붙인다. 발행 전에 사람이 원문에서
대조할 수 있어야 하기 때문이다. 본문에는 쪽수를 쓰지 않는다 — 독자가 볼 것이
아니다. 화면에는 고른 구간의 **번호와 첫 줄**을 보여 준다. 엉뚱한 데를 골랐으면
본문을 만들기 전에 알아야 한다.

**못 골라도 막지 않는다.** 실패하면 앞부분으로 떨어지되 화면에 이유를 남기고
자취에 `failed` 를 남긴다. 조용히 되돌아가면 왜 엉뚱한 근거가 들어갔는지 나중에
알 방법이 없다. 이때 구간 목록은 비운다 — 앞에 걸린 쪽은 고른 것이 아니라 그냥
앞이라 걸린 것이고, 그것을 구간으로 남기면 근거 단계가 표지를 "이 문서가 다루는 것"
으로 읽는다.

사람이 구간을 고쳐 쓰는 화면은 없다. 얼마나 자주 틀리는지 데이터가 없어서,
`response/` 에 "어떤 쪽 목록을 줬더니 뭘 골랐나" 가 쌓이는 것을 먼저 본다.

`pdftotext` 가 여러 단 문서에 더 낫지만 poppler 설치가 필요하다. 이 서버는
윈도라 파이썬만으로 되는 쪽을 골랐다.

받지 않는 것이 다섯이다. 검증에 걸리면 파일을 남기지 않는다 — 못 쓸 파일이
폴더에 쌓이면 나중에 무엇을 지워도 되는지 알 수 없다.

| | |
|---|---|
| 확장자가 `.pdf` 가 아니다 | 거절 |
| 앞머리가 `%PDF-` 가 아니다 | 거절. 확장자는 바꿔 달 수 있다 |
| 20MB 를 넘는다 | 거절 |
| 글자가 안 나온다 | 거절. 스캔본이라고 알려 준다 |
| 글자가 너무 많다 | 거절. 나눠 올리라고 알려 준다 |

### 큰 문서는 자르지 않고 거절한다

파일 크기로는 무게를 못 잰다. 조밀한 30쪽이 성긴 200쪽보다 무겁다. 그래서
**글자 수로 재고 쪽 수는 세지 않는다.**

| | | 무엇을 막나 |
|---|---|---|
| `MAX_CHARS` | 400,000자 | 문서 전체 |
| `MAX_LIST` | 60,000자 | 쪽 고르기 프롬프트에 실릴 쪽 목록 |

`MAX_LIST` 는 쪽 수 × `PEEK` 로 어림잡지 않고 실제로 실릴 만큼
(`min(쪽 글자수, PEEK)` 의 합)을 센다. 짧은 쪽이 많으면 훨씬 작다.

**자르는 선택지도 있었다** — 넘으면 `PEEK` 을 줄여 앞머리를 짧게 싣는 것.
안 한 이유는, 그러면 쪽 고르기가 실패했을 때 그게 문서 탓인지 신호가
얇아서인지 사람이 구별할 수 없기 때문이다. 그리고 잘라 넘긴 문서가 카드에
"출처 확인됨" 으로 뜨는 것은 이 파이프라인에서 이미 한 번 났던 사고다.

**거절이 막다른 길이면 안 된다.** 800쪽 규정을 근거로 쓰고 싶은 것은 정당한
요구이고, 실제로 노리는 것은 그중 특정 장 하나다. 그래서 거절 문구가 실제
글자 수와 "필요한 장만 나눠 올리라"를 함께 말한다. 쪼개 올리면 쪽 목록이
짧아져 모델이 더 정확히 고르기도 한다.

**두 수 다 재서 정한 값이 아니다.** 실제 규정 원문이 쪽당 2,000~3,000자쯤
되므로 대략 150~200쪽에서 걸린다고 보고 잡았다. 거절은 `choice/` 에
`rejected` 로 남으므로, 무엇이 얼마나 자주 걸리는지 쌓인 다음에 조정한다.

## 올린 파일을 추적한다

파일은 `uploads/{sid}/{id}.pdf` 에 **우리가 만든 id 로만** 저장된다. 사용자가
준 이름을 경로에 쓰면 `../` 하나로 폴더 밖에 쓸 수 있기 때문이다. 그래서
폴더만 열어서는 어느 파일이 무엇이었는지 알 수 없다.

**원래 이름이 남는 곳은 로그다.** 올릴 때 `choice/` 에 `uploaded` 한 줄이
붙는다 — id, 원래 이름, 쪽수, 글자수, 내용 지문(`sha`), 그리고 쪽 고르기가
무엇을 골랐는지.

`sha` 는 파일 내용의 지문이다. `id` 는 올릴 때마다 새로 나므로 같은 문서를
두 번 올렸는지 `id` 로는 알 수 없다.

쪽 고르기 응답(`response/`)에도 같은 `doc` 이 붙는다. 그래서 한 번에 읽힌다.

```
/api/logs?kind=uploaded      올린 문서 전부
/api/logs?kind=rejected      거절된 것 전부
/api/logs?doc=6f4c74505c81   그 문서가 지나온 자취
```

```
uploaded   evidence        EU 이행규정 2025.pdf · 57쪽 · 15,755자 · segs [25, 26, 57]
generated  evidence_pick   3건 — 25쪽 · 26쪽 · 57쪽
```

**어떤 파일을 넣었을 때 모델이 무엇을 했는지**가 조인 없이 한 줄로 읽힌다.
쪽 고르기가 얼마나 자주 엉뚱한 데를 고르는지는 이 기록이 쌓여야 안다.

저장 이름은 우리가 만든 id 다. 사용자가 준 이름을 경로에 쓰면 `../` 하나로
폴더 밖에 쓸 수 있다. 화면에 보일 이름만 따로 다듬어 둔다.

근거 단계 프롬프트에는 올린 문서의 제목과 앞부분을 함께 넘긴다. 안 넘기면 사람이
이미 올려 둔 규정 원문을 "규정 원문에서 확인할 것" 으로 또 내놓는다 — 손에 있는
근거가 확인 대기 목록으로 되돌아간다.

## 근거는 고른 것과 쓴 것을 함께 담는다

하나만 고르는 단계(독자·각도·제목·구조)는 둘 중 하나다. 직접 쓴 값이 있으면
그것이 확정값이 된다 — 독자도 각도도 제목도 하나여야 하고, 고른 것과 쓴 것을
동시에 담을 자리가 없다.

**근거는 다르다.** 성격이 다른 것을 나란히 놓는 자리라서 넷이 함께 담긴다.

| 어디서 | 확인 상태 |
|---|---|
| 소재에 딸려온 기사 | 확인된 출처 (`url`) |
| 올린 PDF | 확인된 출처 (`file`) |
| 프롬프트가 만든 확인 대상 | 미확인 |
| 사람이 직접 쓴 근거 | 미확인 |

예전에는 직접 쓴 값이 이겨서 고른 것이 통째로 사라졌다. PDF 를 올려 고른
다음 근거를 한 줄 더 적으면 문서 쪽이 없어졌다.

가르는 기준은 `Step.multi` 다. 단계 이름으로 분기하지 않으므로, 나중에 여러 개를
담는 단계가 더 생기면 그쪽도 같이 동작한다. 화면도 같은 플래그를 보고
`picker` 를 `both` 모드로 켠다 — 카드를 골라도 쓴 것이 지워지지 않고, 써도
고른 것이 풀리지 않는다.

자취에는 `chosen` 과 `written` 이 한 행에 같이 남는다.

## 화면은 단계 이름으로 분기하지 않는다

업로드 상자는 `evidence` 라서 그려지는 게 아니라, 백엔드가 준 단계 정의에
`upload: true` 가 있어서 그려진다. 파일은 끌어다 놓거나 골라서 올리고, 여러 개를
한 번에 받되 서버로는 하나씩 차례로 보낸다 — 한꺼번에 보내면 어느 것이 왜
거절됐는지 알 수 없다. `multi`·`custom` 과 같은 방식이다.
나중에 다른 단계가 파일을 받게 되면 그 단계 폴더의 `Step(upload=True)` 한
줄이면 되고 화면 코드는 안 바뀐다.

## 층 나누기

**백엔드는 값만 준다. 마크업과 CSS 클래스 이름은 프론트에만 있다.**
`grep 'class=' backend/*.py` 가 걸리는 곳은 `render.py` 뿐이고, 그건 화면이
아니라 **결과물로 내보낼 블로그 HTML** 이다. 다른 일이다.

모듈 의존 방향은 위에서 아래로만 흐른다.

```
payload   없음                                    스키마. 아무것도 모른다
llm       없음                                    프롬프트 호출
steps     없음                                    단계 정의
feedback  없음                                    평가 로그
skeletons 없음                                    유형별 권장 구조
figures   없음                                    도식 컴포넌트
options   llm, payload, skeletons, fake           선택지 생성
write     llm, figures, skeletons                 본문 작성
render    figures, fake                           결과물 조립
session   options, write, steps, llm, feedback    상태
deps      session, steps, llm                     거절 판정
api       위 전부                                 엔드포인트
```

`render` 가 `options` 를 보던 것을 끊었다. 결과물 조립이 LLM 을 호출하는 모듈에
의존하는 건 방향이 거꾸로였다. 스키마를 `payload.py` 로 빼서 둘이 그것만 본다.

프론트도 같다. `api.js` 만 백엔드 주소를 알고, `ui.js` 는 백엔드를 모르고,
`shape.js` 는 단계별 형식만 안다. 화면 파일(`pages/*.js`)에는 단계별 분기가 없다 —
`Shape.detail(단계, payload)` 가 형식을 모르는 단계에는 `null` 을 주고, 그러면
카드가 지금까지와 똑같이 그려진다.

## 카드 펼치기

`UI.card` 에 `detail` 을 주면 펼침 영역이 생기고, `copy` 를 주면 복사 버튼이 붙는다.
안 주면 지금까지와 똑같은 카드다. 두 값은 `shape.js` 가 payload 로부터 만든다.
독자나 근거 단계로 넓히려면 `shape.js` 의 `BY_STEP` 에 항목을 더한다.

여러 카드를 동시에 펼 수 있다. 후보를 나란히 비교하는 게 이 화면의 목적이라,
하나를 펴면 나머지가 접히는 아코디언은 맞지 않는다.

복사할 문자열은 HTML 에 심지 않고 `step.js` 가 `{카드 id: 문자열}` 로 들고 있다가
`UI.expand()` 에 넘긴다. HTML 에 심으면 이스케이프 왕복이 생기고 줄바꿈이 죽는다.

`navigator.clipboard` 는 LAN 으로 열면(`http://192.168.x.x`) 막힌다 — 보안
컨텍스트가 아니어서다. 그때는 숨은 textarea 로 떨어진다.

## 후보를 언제 다시 뽑나

한 번 뽑은 후보는 드래프트에 붙어 있다. 화면을 다시 열어도 같은 후보가 나온다.
앞 단계 값이 바뀌면 프롬프트 입력이 달라지므로 알아서 다시 뽑는다.
같은 입력으로 다른 후보를 보려면 `?refresh=1`.

캐시가 없으면 확정이 깨진다. 고른 `id` 를 확정할 때 다시 찾는데, 그 사이 후보를
새로 뽑으면 같은 `id` 가 다른 내용을 가리켜 오류 없이 엉뚱한 값이 확정된다.

## 직접 쓰기

한 칸에 한 줄을 쓴다. 독자·각도는 그 한 줄이 그대로 핵심 값이 되고,
부속 항목만 `{단계}_written.md` 프롬프트가 채운다.

| 단계 | 사람이 쓴 것이 들어가는 자리 | 채워지는 것 |
|---|---|---|
| 독자 | `role` | `expertise_level`, `decision_authority`, `pain_points`, `preferred_terms`, `avoid_terms` |
| 검색의도 | `question` | `search_intent`, `sub_questions`, `desired_action` |
| 각도 | `core_message` | `viewpoint`, `tone` |

사람이 쓴 말은 코드가 그대로 넣는다. 프롬프트는 그 필드를 아예 출력하지 않도록
막아 뒀다. 채우기가 실패하면 막지 않고 최소 정보로 진행하고, 확정값 `detail` 에
실패했다는 표시가 남는다.

유형은 직접 쓰기를 받지 않는다 (`steps/type/` 의 `custom=False`). 정해진 여섯 개
밖의 값이 들어오면 구조 단계 골격 매칭이 조용히 실패한다.

## 아직 없는 것

- 네이버 썸네일에 문구를 얹는 일이 아직 없다. 배경 그림만 만들고 문구는 사람이 얹는다 — 생성 모델이 한글을 못 쓰기 때문이고, 도식을 마크업으로 그리는 것과 같은 이유다.
- 수치 차트와 데이터 표가 없다. 도식 컴포넌트는 넷뿐이다.
- `structure_strategy` 를 두지 않았다. `article_type` 과 역할이 겹치고, 사람이 고른 유형을 모델이 덮을 수 있다.
- **이미지가 없다.** 대표 이미지와 네이버 썸네일은 아직 만들지 않는다.
  결과물에 `<!-- HERO_SLOT -->` 주석과 확인 목록 한 줄만 남는다.
- 네이버 도식은 자리표시 한 줄이다. 홈페이지 쪽 도식을 사람이 이미지로
  저장해 넣어야 하는데, 그 저장 버튼이 아직 없다.
- 제목 단계에 넘기는 키워드는 아직 `fake.py` 값이다. 키워드 정리 단계가 없다.
- 직접 쓴 제목·근거는 부속 필드가 빈다. 지금은 아무도 안 읽어서 문제가 아니다.
  본문 작성 단계가 붙어 `claim_to_verify` 를 읽기 시작하면 그때 채워야 한다.
- 근거 단계는 검색을 안 한다. "무엇을 어디서 확인할지"까지만 만들고 URL 은 없다.
- 화면에 "다시 뽑기" 버튼은 없다. API 는 `?refresh=1` 로 이미 받는다.
- 직접 쓴 제목·근거는 부속 필드가 빈다. 구조는 이미지 계획까지 읽지만 제목의
  `title_style` 이나 근거의 `claim_to_verify` 는 아직 아무도 안 읽어서 비워 둔다.
  남긴 평가를 프롬프트에 되먹여 다시 뽑는 것도 아직 없다. 평가는 쌓이기만 한다.
- 2~9단계 평가에는 이유 칩이 없다. 무엇이 반복되는 이유인지는 메모가 쌓여야 안다.
- CTA 는 `<!-- CTA_SLOT -->` 주석만 있다.
- 드래프트는 메모리에 있다. 서버를 껐다 켜면 날아가고 세션당 하나다.
